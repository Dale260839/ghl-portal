## Delivered — the parts that needed no keys

**GHL API client.** Auth headers, timeouts, typed errors, and a retry policy
separating retryable from permanent. 429 honours `Retry-After`; 5xx and network
failures back off; **401 and 400 never retry**. Backoff is jittered — the hourly
sync-back fires every project on the same schedule, and unjittered retries would
hit the rate limit in lockstep.

**Response mapper.** The only file that is guessing, quarantined on purpose so a
wrong guess is a one-file fix. Checkbox coercion defaults to **false**:
`Client Portal Enabled` is a clause of the §9.1 gate, so an unparseable value
must close it, never open it.

**`GhlDataSource`.** Implements the interface the screens already use.
All-or-nothing: a half-configured environment falls back to fixtures with a
warning rather than half-working.

**WF1 + WF2 as pure planners.** Trigger in, typed effects out — no network, no
clock, no credentials. §11 is still the specification even though D-002 moved the
implementation, so each is asserted against it action by action.

- **WF1** does all ten §11 actions. Refuses a payload without a valid shared key
  rather than inventing one. Idempotent — a re-fired handoff records activity
  instead of duplicating seven milestones. Flags an unassigned PM loudly, since
  an unassigned project has nobody to receive the review queue, which quietly
  breaks the §3.2 approval path.
- **WF2** won't act without the shared key rather than falling back to name
  matching (§3.6 forbids exactly what a helpful implementation would do here),
  rejects stages outside the §7 pipeline, and no-ops on a re-fired webhook so a
  client isn't told twice about the same stage.
- **On Hold and Canceled do not move the progress bar.** A project paused at 65%
  has not regressed to 0, and showing that to a homeowner would be alarming.

## Enforcement — automated, not hand-checked

Client reads apply the §9.1 gate, then build an explicit **allow-list** DTO
rather than filtering a deny-list — a new internal field cannot reach a client by
default. `assertNoInternalFields` is the backstop, and the server-only guard is
structural: pull it into a client component and the build fails.

This morning's checks were manual curls, which proves it was safe today. They are
now 14 tests, including value-level checks that survive a field rename.

| Check | Result |
|---|---|
| Original estimate, markup, margin, internal notes, delay reason in a client projection | **0** |
| Unpublished / internally-approved updates reaching a client | **none** |
| A contact projecting a project they aren't associated with | **denied** |
| Switches off → budget, team, completion date | **withheld** |

**88 tests** — 54 web (14 gate/leak · 19 transport & mapper · 21 workflow), 34 contracts.

## Specification gaps found today

Building against §11 surfaced three things it requires but never defines. All
isolated in `workflows/defaults.ts` as provisional tables, recorded as **W1–W3**
in `KICKOFF.md` §5, each a one-table edit once Chris confirms:

| # | Gap | Current |
|---|---|---|
| **W1** | WF2 must "update Progress Percentage" — **no mapping given** | Straight line anchored on the two figures §11 does state: 10% at creation, 100% at Completed |
| **W2** | WF1 must create "default milestones/tasks" — **neither list exists** | Seven milestones, two tasks. Thin on purpose — a wrong default task on every project is noise a PM clears by hand |
| **W3** | WF2 notifies the client "**when appropriate**" — undefined | Six stages, biased toward silence. Over-notifying gets a portal muted, and then the notifications that matter are missed |

Earlier in the day, transcribing the architecture also surfaced the 19-vs-20
stage-count contradiction, an unspecified AND/OR in the financial gate, and a
switch (`Show Schedule to Client`) that is named but never mapped to any field.
