**Two knock-on effects that need saying out loud:**

- **Phase 0 Test B was invalidated and has been rewritten.** It existed to prove
  AI Studio could bind live per-client data. We aren't using AI Studio, so it
  proved nothing. It now tests the same underlying risk through the GHL API —
  same hour of effort, still the right gate. See `docs/PHASE-0.md` §3.
- **Phase 6's distribution model shrinks.** The snapshot no longer carries the
  front-end *or* the workflows — it ships objects, fields, pipeline, forms,
  templates, roles, and portal settings; the app, workflows, and sync-back job
  deploy separately per sub-account. "Build once, snapshot everywhere" was the
  multiplier this project was justified on, and it is materially smaller now.
  **Chris and Pat need this before Phase 6, not during it.**

**Standing guardrails now in `CLAUDE.md`:** Supabase is production — never alter
a table; ask before any write to a live system; never invent a fallback that
writes.

## Delivered — the demo

`npm run dev`, then sign in as any of three identities (no password):

| Email | Experience |
|---|---|
| `marcus@allianceproservices.com` | Contractor Dashboard |
| `tony@allianceproservices.com` | Field Interface |
| `dana@example.com` | Client Portal |

**Contractor** — Portfolio Overview with KPIs and an attention list · Projects
List · Project Overview with timeline, financials, and visibility switches ·
Field Update review queue carrying all seven verbatim actions.
**Field** — mobile-first today view, tasks, daily update form.
**Client** — project switcher (two projects), progress, schedule, budget
summary, published updates.

### The loop to walk the client through

1. As **Tony**, submit a daily update. The form has two separate note fields and
   no publish button anywhere on it.
2. As **Marcus**, open Field Updates. It's `Pending`. Internal notes flagged in
   red; client summary editable.
3. **Approve and Publish**.
4. As **Dana**, the update appears — edited summary only.

Clickable, not narrated. There's also **"See what the client sees →"** on the
contractor's project page, which renders the portal through the same gate so the
difference is visible side by side.

## Enforcement — verified, not asserted

Client reads run through `client-view.ts`: `server-only` (build fails if it's
ever pulled into a client component), the §9.1 gate, then a projection onto an
explicit **allow-list** rather than a deny-list filter — so a new internal field
cannot reach a client by default.

Smoke-tested against the running app:

| Check | Result |
|---|---|
| Original estimate, markup, margin in portal HTML | **0 occurrences** |
| Internal field notes in portal HTML | **0 occurrences** |
| Unpublished update visible to client | **absent** (correct) |
| Published updates visible | present |
| Dana requesting another client's project by URL | returns her own — no leak |

Those fields aren't hidden by the template. They are never read.
