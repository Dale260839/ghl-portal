## Live data, for the first time

`/dashboard/buildsuite` reads BuildSuite's Supabase directly and renders real
projects — 43 active, with counts across `matched` / `new` / `draft` /
`completed`. Badged **"Live data"**: the inverse of the fixture banner, because
the notable thing about this screen is that it isn't a demo. A read failure shows
an error rather than quietly falling back to fixtures.

**Read-only by construction, not by promise.** D-003 says never alter that
database, and D-010 showed the key permits more than it should, so:

- The client exposes exactly two methods — `select` and `count`, both GET. There
  is no `insert`/`update`/`delete`/`rpc` to reach for by accident, and a test
  asserts that surface stays that way.
- **`select(*)` is refused**; columns must be named. That stops a schema addition
  on Sing's side silently widening what we pull, and keeps us out of columns we
  have no screen for — `client_email`, `client_phone`, `scope`, `sow_data`,
  `documents` are deliberately not selected even though the key would return them.
- `count()` uses PostgREST's `Content-Range`, so status tallies transfer no rows.

Column names came from the live schema, not guesses.

| # | Decision | Effect |

| **D-005** | BuildSuite's API has **no machine authentication** — every endpoint needs a `bs_session` cookie from the GHL login flow | `BUILDSUITE_API_KEY` never existed. A scheduled server-to-server job cannot call it. |

### D-010 is the one that needs a decision from Chris

`projects` has **53 columns and none of them is a BuildSuite Project ID.** No
`bsp_*`, no `BSP-` value in any sampled row. What every row *does* carry:
`ghl_contact_id` and `ghl_opportunity_id`.

BuildSuite already links to GHL, using GHL's own identifiers. The shared key we
specified doesn't need inventing — a working one is in place on both sides.

**Recommendation: adopt `ghl_opportunity_id` and amend ARCHITECTURE §5/§3.6**,
rather than ask Sing for a production schema change plus backfill to introduce a
duplicate key. §5's real requirement is *one immutable shared key, never match on
name or address* — `ghl_opportunity_id` satisfies it. The `BSP-` format was a
preference, not the requirement.

Cost if approved: roughly a morning. `ids.ts` and the handoff contract currently
**reject** anything that isn't `BSP-YYYY-NNNNNN`, so they need reworking. I'd
rather not build further on a key that doesn't exist.

### A conflict worth catching now

D-006 has the Hub using `bs_session`, which is scoped to `.buildsuite.ai`.
ARCHITECTURE §2 puts the contractor surfaces at `projects.<contractordomain>`.
**A cookie scoped to one domain is never sent to the other** — that's a browser
rule, not a config option. So either the Hub lives under BuildSuite's domain, or
it owns its own GHL-backed session. **Recommending the latter:** option one is
faster but permanently couples the Hub's URL to BuildSuite's domain, and
un-picking it later means re-authenticating every user on every sub-account.

## For Sing — one security item

The **publishable** key reads `contractors` including `full_name` and `phone`; we
saw a real contractor's mobile number on the first row. Publishable keys are
designed to be embedded in browser bundles, so in practice that table is readable
by anyone who has ever loaded BuildSuite's front-end.

Not our table and we won't touch it — but far cheaper to fix before someone
notices. Either RLS should scope it or the Hub gets a differently-scoped key.
Written up in `What_We_Need_From_Sing.md` as information, not a request.

It also corrected an assumption of mine: I'd expected the read key to be
RLS-restricted. It isn't, for those tables. We read only `projects` and treat the
rest as off-limits regardless of what the key permits.
