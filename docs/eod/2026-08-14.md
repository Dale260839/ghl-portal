## The session was forgeable

The cookie was plaintext JSON. `httpOnly` stops a page script reading it but does
nothing about the person holding the browser — and since **tenancy now comes from
the session** (D-012), anyone could edit `authProfileId` in devtools and read
another contractor's projects. The tenancy work last week was only as strong as
the cookie carrying it.

Now HMAC-signed and versioned, with:

- **timing-safe comparison**, and unequal lengths short-circuit before the compare
  so length itself doesn't leak;
- **an 8-hour expiry**, checked independently of the signature;
- **the signature verified BEFORE the payload is parsed** — attacker-controlled
  JSON should never reach `JSON.parse` on an unverified token, or a session bug
  becomes a parser bug;
- **production refuses to start without `SESSION_SECRET`.** Generating one would
  silently log every user out on each deploy and, worse, hide that it was never
  configured. Development generates one per process, so `npm run dev` needs no
  setup.

The test that matters does exactly what an attacker would: decode the cookie, swap
the tenant id, re-encode. Rejected.

## Auto-login is built and waiting on the menu link

`/api/auth/ghl` exists, is tested, and is env-vars away from working. When Chris
creates the Custom Menu Link, this is configuration.

**The security point, stated where someone will read it:** merge-field query
parameters are **not authentication**. They arrive as clear text in a URL, so
anyone who learns the callback address could request it with a `locationId` they
invented — and because tenancy comes from the session, that means choosing whose
data to receive.

So:

- a landing is trusted only when **signed**, and the signature covers every
  identity field;
- signed links **go stale after five minutes**, because otherwise a URL in a
  browser history or a screenshot is a permanent key to that account;
- with nothing configured the landing is **refused**, not trusted;
- the development escape hatch is opt-in, **labelled in the result**, and ignored
  whenever a secret is set — so it can't silently disable auth in production.

**Tenant resolution** matches on email **and** `location_id`, which `auth_profiles`
carries — checked against the live schema, not assumed. Two matches returns null
rather than guessing; picking one would silently put someone in the wrong tenant,
and a support ticket beats a breach. That lookup is the one read in the system
that crosses tenants by necessity, so it selects a single id and nothing
enumerable.

## Deploying, once the domain exists

1. Vercel → Root Directory at repo root (not `apps/web`) so `vercel.json` applies.
2. Environment: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and a generated
   `SESSION_SECRET`. Those three and it runs — BuildSuite data live, the rest on
   fixtures with the banner.
3. Add `GHL_MENU_LINK_SECRET` when the menu link exists; auto-login then works
   with no code change.
