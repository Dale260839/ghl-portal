## The client gap, closed

The client compared our portal to a twelve-screen demo and called ours backward.
The count was twelve to one, so that was fair about what was visible.

Screen by screen, **two were built and ten were already modelled** — the model
had anticipated all of it, the plan had just sequenced it later. So the fix was
reordering, not redesigning.

**Now: all twelve exist.** Six built — Project Timeline, Schedule, Daily Updates,
Documents, Photos, Messages — and six designed placeholders that say what's
coming. A client who clicks a nav item and gets a 404 concludes the product is
broken; one who reads what's coming concludes it's being built. The demo does the
same on its own Completion & Warranty screen.

Both surfaces now share one sidebar shell with count badges, so the dashboard and
the portal read as one product rather than two apps sharing a database.

**One detail that proves something:** the fixtures include a deliberately
withheld supplier invoice and a withheld photo of damaged goods. A documents list
showing everything proves nothing; one that visibly withholds proves the gate is
real.

## Auto-login from GoHighLevel

Working end to end against the live account:

```
/auth/ghl?locationId=IifYfP2B2NUaoDPdsTTa
  → verified the location with GHL     Alliance For Contractors, Spokane WA
  → resolved 2 admin profiles
  → issued a signed session
  → dashboard showed 8 live projects
```

**Seeing BuildSuite's real menu link changed the design.** Its callback is
`?locationId=IifYfP2B2NUaoDPdsTTa` — one parameter. That said something we had
wrong at a deeper level: **the tenant is the sub-account, not a person.** We had
built for a user id, an email, and an HMAC signature GHL cannot produce.

That correction caught a bug that would have been quiet and damaging. The
Alliance location has **two** admin profiles owning nine projects between them.
Our code scoped to one profile — which would have hidden half an agency's own
work from itself, and looked like data loss rather than a scoping error.

**Three findings measured against the live API, not assumed:**

1. **GHL does not substitute merge fields in Custom Menu Links.** A link saved as
   `?locationId={{location.id}}` delivers the literal braces. That is why
   BuildSuite's link carries a hardcoded id. Consequence: one menu link per
   sub-account until a Marketplace app replaces it.
2. **GHL returns 403, not 404,** for a location our token cannot reach. The
   forged-link case was falling through to the outage branch and reporting
   "couldn't reach GoHighLevel" — sending someone to check their wifi when they
   should have been checking the link.
3. **Our config was blocking sign-in on a value sign-in never uses.** It demanded
   all five GHL variables including the custom-object key. Auto-login needs three.

Every auth failure now names its own cause, because an unhelpful error costs an
afternoon of looking in the wrong place.

**The authenticating page** is what a contractor sees between clicking the menu
item and landing on the dashboard — the same moment BuildSuite shows. It renders
"signing you in" and nothing more until verification passes; the face must never
imply success before the check has run.

## Supabase — the Hub's own tables

The Hub now stores its operational records in **new tables it creates**, prefixed
`hub_`. Create-only: no `ALTER`, no `DROP`, nothing of BuildSuite's touched.

Two things the migration gets right that the existing schema does not: **RLS
enabled, deny-by-default, on every table** — the publishable key can already read
`contractors` including phone numbers, and we are not repeating that — and **both
tenancy keys on every row**, so a row cannot be read without knowing whose it is.

**Not run.** The app's publishable key cannot execute DDL, which is correct — a
running application should never be able to change its own schema. It needs the
service-role key or the SQL editor, **and Sing's sign-off, since it is his
database.**

## Blocked

because the credentials were never added there — `GHL_API_BASE_URL`,
`GHL_API_VERSION`, `GHL_PRIVATE_INTEGRATION_TOKEN`, then a redeploy. It works
locally against the same live account, so this is configuration, not code.

**The menu link needs the real sub-account ID**, not `{{location.id}}`.

**`GHL_PROJECT_OBJECT_KEY`** — the GHL half stays on fixtures without it.

**The `hub_` migration** needs running by someone with the service-role key.
