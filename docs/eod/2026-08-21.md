## Real data, and what BuildSuite actually has

The dashboard, project list and project detail now read **BuildSuite's live
Supabase** instead of fixtures. 27 real projects for the signed-in profile,
their real clients, addresses and dates.

**I measured the schema before mapping anything**, and two findings changed the
design:

**`exact_budget` is empty on every row.** BuildSuite records a *band* —
"$50,000 - $100,000". A band is not a number, and parsing a midpoint out of one
would put a fabricated figure on a contractor's dashboard. So the money fields
stay at zero, the real band is carried through, and screens show the band or
nothing.

**`ghl_opportunity_id` is empty on every row**, so it cannot be the join key
yet, whatever D-010 settles on.

Also empty everywhere: `street_address`, `trade`, `project_type`.

**What I did not do:** map BuildSuite's status (`active`, `draft`) onto the §7
nineteen-stage pipeline. The architecture is explicit that this is lossy both
ways, so BuildSuite-sourced projects show their own status word and no stage.

**One thing that was quietly wrong and is now fixed:** every project row
rendered `0% · On Track · $0`. That is not missing data — it is three confident
statements nobody made. Progress, health and money are now suppressed where the
source does not carry them.

## The correction that mattered

I built a fact-check that read every technical claim in the presenter script
against the actual code. It caught a claim I had made repeatedly, including to
Dale directly:

**I said the contractor dashboard was reading live BuildSuite data. It was
not — it was on fixtures.** The data layer falls back to sample data until
`GHL_PROJECT_OBJECT_KEY` is set, and even when set that path reads GoHighLevel
custom objects rather than Supabase.

Why it mattered: there is an amber "Demo data" banner across the top of that
screen. Saying "these are live numbers" would have been contradicted by the page
mid-sentence, in front of the client we are trying to win back.

Two smaller corrections from the same pass: the read-only guarantee lives in our
database client, not in the key (the key is the publishable one against tables
with no row-level security); and the tenancy claim now says *staff-side* reads,
because two client-side reads deliberately take no tenant.

## The presenter HUD

A **self-contained HTML file** — no server, no wifi, no build. Twenty-two
walkthrough steps plus a seven-step architecture annex.

Each step gives the primary message, a drawing of the screen with the exact
target ringed, where to put the mouse, what to say, what to avoid saying, the
likely objection, and what to do next. **Presenter mode** strips it to four
large blocks for use while actually talking.

**The screen maps are scraped from the running app, not drawn.** The first
version was drawn from memory and was wrong in ways that send a presenter's
mouse to the wrong place: the client portal was drawn with eleven nav items when
it has thirteen, the project detail panels were invented, and the review screen
was drawn with three buttons when it has four. Anything hand-drawn drifts the
moment a screen changes, so now `npm run hud:maps` re-reads the real pages.

## The demo data toggle

Wiring real data made the demo *worse* in one specific way: BuildSuite holds no
field updates, so the review queue is empty — and the review queue is the spine
of the walkthrough.

The choice was between mixing fixture updates into a list of real projects,
which is indistinguishable from the product working, or a deliberate labelled
switch. **There is now a Demo data toggle in the header**, beside the account
switcher. On: six fixture projects and a full review queue. Off: the tenant's
real projects. Loud when on, because a contractor who forgets it is flipped
would read sample content as their own book of work.

It also swaps the tenant, and has to — the fixtures belong to invented profiles
that overlap a real session by exactly one. Every read is still scoped and still
filtered; the identity behind it is simply pretend.

## Smaller things

**The active nav highlight never moved.** Links worked; the highlight stayed on
whichever page you first landed on. App Router layouts do not re-render when you
navigate between their children, so reading the path from a header in the layout
was correct once and stale forever after. Verified across five dashboard routes,
all thirteen portal routes, and the nested project pages.

**Internal notes were red**, which says something has broken. They are now
amber. Red keeps a clear job: genuine bad states and real failures.

## Blocked

`GHL_PRIVATE_INTEGRATION_TOKEN`. Auto-login still refuses on the deployed site.
Add `SUPABASE_URL` and `SUPABASE_ANON_KEY` too if the deployed site should show
real projects rather than fixtures.

**The `hub_` migration** needs running by someone with the service-role key.

**Two dependencies on the BuildSuite side**, both about *which* projects we
show rather than how. The client-to-contractor matching is unfinished, so there
is no reliable join from a contractor to the deal they closed. And we cannot
locate how a contractor bid is classified in the schema. Until both land, the
project list is broader than it should be — it includes work that is not signed.
