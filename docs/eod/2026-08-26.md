## The migration was building a second system

Our unrun migration created eleven tables: milestones, schedule, daily updates,
acknowledgements, comments, messages, documents, photos, and more with Phase B.

**All four documents give those records to GoHighLevel after handoff**, and they do not
disagree with each other about it. Sing's own review says it plainly:

> *"Everything else is created inside GHL after handoff … that separation is what keeps both
> systems clean."*

Those tables would have been a second home for records GHL owns. Two systems writing the same
operational record is how a project ends up in two states with nothing to say which is right —
the exact failure the one-directional handoff exists to prevent.

**It is now three tables**, and only what the Hub genuinely owns:

| Table | Why the Hub owns it |
|---|---|
| `hub_publication_decisions` | The PM's approve / edit / publish choice — *"the PM decision buttons live in the Hub only, nothing in GHL"* |
| `hub_visibility_settings` | The client-visibility switches, which are clauses of the gate this app enforces |
| `hub_media` | Photos and documents tagged per contractor |

`hub_media` stores **metadata and a pointer, not the bytes**, so it works whether media ends up
in Supabase or in the contractor's GHL storage. That decision was blocking; it no longer is.

**Timing is the whole point.** The migration has never been run, so correcting it cost nothing.
Running it as written would have committed us to the shape the architecture exists to prevent,
and unpicking it later means migrating live records.

## Ten tests that fail when someone drifts

The five rules from the Aug 21 huddle are architectural properties, not behaviours. They cannot
be caught by exercising a function, because the failure is somebody adding a *new* code path
months from now — a stage write in a page, a GoHighLevel import in the field route, a lookup
keyed on a project name.

So these tests read the source and assert properties of the codebase:

1. **Nothing sets a project stage except the workflow reflecting GoHighLevel.** Stage movement
   belongs to GHL; the Hub mirrors it.
2. **The field surface imports nothing from the GHL client**, and a field user has no publish
   action available.
3. **No lookup matches a project by name, title or address.** A rename breaks the link silently
   and — the huddle's own words — *"shows the wrong data on a job site."*
4. **The Hub's mutating actions are the publish decision and session control, nothing else.** A
   new server action fails the test until someone justifies it.
5. **The migration creates no table for a record GoHighLevel owns**, still enables RLS on every
   table, and still alters nothing of BuildSuite's.

**I mutation-tested them rather than trusting a green run.** Adding a fake `hub_daily_updates`
table failed two; adding a rogue `deleteProject` action failed another. Then restored and
re-verified. A guardrail test that cannot fail is decoration.
