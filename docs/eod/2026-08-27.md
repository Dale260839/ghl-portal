## The webhook receiver — the third wire

D4 §3 is the only document that states it plainly, and it is the piece most easily missed:
*"custom values alone do not trigger anything. GHL must be told to notify the Hub via webhook
when values change. So firing = webhook + key."*

Nothing in the build verified a webhook. Now `POST /api/ghl/webhook` does.

**Refuse-by-default when the secret is absent, in every environment.** There is deliberately no
development bypass — an unverifiable webhook is not a webhook, and a dev-only bypass is one
environment variable away from being a production one. That case answers **503, not 401**,
because it is our configuration missing rather than their credential failing, and whoever reads
a delivery log needs to know whose problem it is.

Four things it gets right that are easy to get wrong:

- The signature is computed over the **raw body**, never a re-serialised object — re-serialising
  changes bytes, and the signature is over what was sent
- Signed over `timestamp.rawBody`, so a captured signature cannot be reattached with a fresher
  timestamp
- The body is parsed **only after** the signature passes, so our JSON parser never runs over
  bytes from an unauthenticated source
- Constant-time compare, with length checked first so a mismatch does not leak length

**Replay is closed twice:** a timestamp window — absolute, so a *future* timestamp is refused
too, since a forward-skewed clock would otherwise widen it indefinitely — plus a seen-id set.
That set is per-instance and serverless means several, so the durable guarantee is the window.
Documented rather than glossed; the fix is a table once webhooks carry something irreversible.

**Unmapped event types answer 200, not 4xx.** GHL will send types we have no planner for, and a
4xx reads as "this endpoint is broken" to whoever watches deliveries — who disables it, and then
the events we *do* handle stop arriving too.

**It stops at the seam deliberately.** It verifies and routes; it does not execute the planner.
Building a trigger needs the GHL record behind the event, and reading that needs the object key
we do not have. GHL's real event names are unconfirmed, so matching tolerates case and
separators and the unmatched branch logs the type precisely — the first real delivery tells us
what to fix.

Verified over HTTP against the running endpoint, not only in unit tests: eleven checks covering
signed, tampered, unsigned, stale, replayed, unmapped, no-location, non-JSON, the GET
registration ping, and that a refusal body leaks nothing about which check failed.

## The field interface, to spec

D4 §5 asks for a mobile-first, app-like surface where the contractor can *"assign tasks in the
notes"* and *"the field person gets a notification/ding."* Ours was one long scrolling page with
a hardcoded name.

**Bottom navigation, not a sidebar** — this is used one-handed on a phone on a job site, and the
bottom of the screen is where a thumb already is. Safe-area padding is not decoration: without
it the last nav item sits under the iPhone home indicator and cannot be tapped at all. Tap
targets at 56px. Four routes now — Today, Tasks, Update, Messages — with the daily update form
moved off the bottom of Today into its own.

**The ding is real.** `Task` gained `assignedTo`, `pmNote`, `assignedAt` and `seenAt`; all four
exist for that one sentence. Unseen assignments carry a nav badge, an amber rule on the card,
and a "Got it" button that clears it. A badge you cannot clear is a badge people stop trusting.

**Crew ↔ PM conversations, internal in both directions.** D2 Step 3: *"do not expose unrelated
client or financial communication."* The thread drops anything client-visible **and** anything
the client wrote — a crew member reading what a homeowner said about them is how a job goes
wrong.

**§9.4 enforced by construction.** A field project omits every money field, so a field session
does not receive `margin: 0` — it receives no margin property at all. The client-visibility
switches go too: they carry no money, but "does the client see the budget" is contractor-side
configuration and no use to a crew member.

Verified with a real field-role session over HTTP: assignments render with their PM note, the
unassigned task stays hidden, and no money string appears on any of the four screens.

## The correction: the contractor side is CRUD

**Raised in review, and right.** I had the contractor dashboard as effectively read-only.

D4 §5 says the PM decision buttons *"live in the Hub only — nothing in GHL … this is the one
place the Hub owns the action."* I read that as a cap: one write, everything else reflects. It
means the publish decision is not **duplicated** in GoHighLevel. §12.1 says the opposite in plain
terms — the contractor dashboard *"creates and controls everything the other two experiences
display"* — and D2 lists create-forms for projects, milestones, tasks, selections, change
orders, issues, messages, punch list and warranty.

So permission is now a **matrix**, closed by default:

| Role | May |
|---|---|
| **Contractor** | Full CRUD on every operational record, plus publish and the gate switches |
| **Field** | Create updates, progress **their own** tasks, raise issues, upload photos, message the PM |
| **Client** | Approve selections and change orders, comment, message, raise issues and warranty requests |

Four exceptions, all of them in the documents rather than invented:

- **`completeStage` is granted to nobody.** GoHighLevel owns stage movement; the Hub reflects
  it. The action exists in the type so its absence from every row is a statement rather than an
  omission, and a test fails if anyone grants it.
- **Publishing is the contractor's alone** — the crew proposes wording.
- **Only a contractor deletes.** A crew member or homeowner erasing a record destroys the audit
  trail the approval model depends on; they correct by adding.
- **No field or client write reaches an invoice**, and neither reads one.

**Permission and ownership are separate, and both must pass.** "May a field user update a task"
is the matrix; "may they update *this* task" is `ownsTask`. Conflating them is how a crew member
ends up able to close somebody else's work.

## The other correction, from late yesterday

This postdates yesterday's EOD, so it is recorded here.

I had cut `0001_hub_tables.sql` from eleven tables to three, because all four documents give
operational records to GoHighLevel after handoff. **That is a requirement about the system
boundary, not an instruction about our database.** GHL custom objects are not reachable — no
object key, tier unconfirmed — so those tables remain the working store. Reverted.

Two things from that pass were real and were kept: a `hub_visibility_settings` table that was
missing entirely, and a tenancy key that two tables lacked — found by a guardrail test rather
than by anyone reading it.

**Both corrections are the same error**, and it is now written into the contributing rules: read
the four documents as requirements, not as technical specification. When one appears to dictate
an implementation detail, that is a reading error.

## On the tests

58 new, 297 total. Two things about them worth recording:

**The guardrails caught me twice today**, which is the argument for having them. Changing the
publish check from a role string to `assertCan` broke the test pinning the old mechanism, and
the money heuristic on field projects flagged `showBudgetToClient`.

**One guardrail was itself wrong and was deleted.** The test asserting "the Hub owns exactly one
write" encoded my misreading *as a test*, which is worse than the misreading — it would have
blocked the correct fix. Replaced with "every mutating action asks permission first", which is
the invariant that actually matters and does not need editing each time a legitimate action is
added.

Both new guardrails were **mutation-tested rather than assumed**: an action that writes without
asking fails one, and granting `completeStage` fails two.
