## The finding

Measured, not inferred. Every number below came out of the production database.

| Step | Count | % |
|---|---|---|
| Deals in BuildSuite | 182 | 100% |
| Linked to a project row | 47 | 26% |
| Matched to a contractor | 5 | 3% |
| Sent to CRM | 2 | 1% |
| Signature sent | 1 | 1% |
| **Signature signed** | **0** | **0%** |

The architecture is right and largely built. The two systems divide cleanly —
GoHighLevel owns ingestion, BuildSuite owns matching and proposals, GHL owns
execution after signing — and both schemas already anticipate the join.

**What is missing is a single signed job.** Every remaining technical task is
small. They are all downstream of one deal getting the whole way through.

That is a better problem than a design flaw, and it should be said plainly
rather than described as an integration gap.

## Day 1 — the Hub reads `deals`

The Hub had never read this table. It reads `projects`, which is the far end of
the pipeline, so everything upstream was invisible: who applied, who was matched,
whether anything was signed. **That invisibility is what hid the finding.**

**It answers the question open since 2026-08-20** — how a contractor bid is
classified as won. Not on `projects`; it is `signature_signed_at` or
`sent_to_crm_at` on the deal. `isSignedWork` is one function because those two
columns can each mean won and they do not arrive together — the signature is
captured first, the handoff fires after. Spreading that judgement across screens
is how two of them start disagreeing. Still needs Sing's confirmation, and the
code says so: the column is empty on all 182 rows, so no sample can prove it.

**The column list is deliberately narrow.** It does not select `access_token` (a
credential), `client_email`, `client_phone`, `photo_urls`, `photo_analysis`,
`metadata` or `signed_pdf_url`. The publishable key permits every one of them;
not selecting them is our half of that exposure, and a test fails if any is added
back.

**Built against the plan, then changed with the reason recorded.** The sprint
called for a `count` request per stage. A per-stage count can only ask about
stages the code already knows, so a status BuildSuite invents would go missing
from the total instead of appearing as its own bucket. One read, counted in
memory.

## Day 2 — the pipeline screen

`/dashboard/pipeline`. The finding stops being something I describe in a message
and becomes a screen Chris can open.

**The data chose the design.** I measured the age spread before picking a stall
threshold: 20 of 23 Alliance deals are past 30 days, the median `draft_ready`
deal is 97 days old, the oldest is 174. A binary stalled flag at *any* value
lights up 87% of the board — and a screen where almost everything is highlighted
has highlighted nothing. So bands: fresh, stalled at 14 days, dormant at 60. The
useful question is not *whether* a deal is stalled but *how badly*.

**Three things made structural rather than cosmetic:**

- **It is occupancy, not flow.** A funnel chart normally reads as "how many
  reached this step". All we have is `status` — where a deal sits now. A deal
  that advances leaves the count it came from. Titled and captioned to say so.
- **Signed and sent-to-CRM are not stages.** They cut across `status`, so putting
  them in the bars would double-count. Separate panel, and a test pins that the
  bars still sum to the total.
- **A zero milestone explains itself; a non-zero one drops the caption.** "No
  proposal has left BuildSuite" is true today and a lie the day one does, so the
  note is nulled in the model rather than hidden by the page. The screen cannot
  outlive its own caption.

**Live only, deliberately not on the demo toggle** (which was then removed
entirely — below). An invented funnel with invented signatures is exactly the
reassuring picture the real data contradicts.

**The live render caught what unit tests would not have.** Budgets displayed as
raw tokens. BuildSuite has **two vocabularies in the same column** — 101 deals
use `5k_10k`/`under_5k`/`100k_plus`, 37 are already written out as
`$15,000 - $50,000`/`$250,000+`, 22 are empty. Tokens are normalized; currency
strings pass through untouched, because reformatting a string someone already
wrote as money is how `$250,000+` becomes subtly wrong.

## Day 3 — the join, and the filter Sing asked for

**The key is `deals.source_project_id → projects.buildsuiteProjectId`** — the
only populated link. `ghl_opportunity_id` is empty on all 182 deals and
`ghl_contact_id` on 180, so neither could carry it today (C-3). Verified live:
every one of Alliance's 8 deals with a project id resolves, and every one of
those 8 projects has a deal pointing back.

**Three states, not two, and this is the decision the file turns on.** A project
is `signed` (has a deal, deal was won), `unsigned` (has a deal, deal was not) or
`unknown` (no deal points at it). **The filter hides only `unsigned`.**

We hide work only when we hold positive evidence it is unsigned. Only 26% of
deals carry a project id, so treating "no deal" as "not signed" would hide most
of the book of work — which to a contractor is indistinguishable from data loss.
The live data supplied the exact case: Alliance has 9 projects, 8 with a deal and
one without, and **two projects both named "Jenkins"** where only one has a deal.
Keying on the id rather than the name is doing real work there.

**A signed deal wins when two deals point at the same project.** Nothing in
BuildSuite forbids it, and otherwise whichever row came back first would decide
whether a contractor sees their own signed job. Tested in both arrival orders,
because only one of them fails if you get it wrong.

**The flag ships off, and that was proven rather than assumed.** With
`ENABLE_SIGNED_ONLY_FILTER=true` against live data the list goes from 9 projects
to 1 — and the survivor only appears because it has no deal to judge. A
contractor opening to that would read the product as broken and be right. The
measurement is written into `.env.example` beside the flag.

## The demo data toggle is gone

Owner's instruction, and removed rather than hidden behind an environment
variable — dead code behind a flag is one variable away from coming back.

**It reached further than a button.** Demo mode also replaced the tenant scope
with a fictional agency, because the fixtures belong to invented profiles that
overlap a real GoHighLevel session by exactly one. That override is gone too, so
`requireTenantScope` now has one path: your session, or a redirect.

Fixtures remain the last-resort fallback when neither BuildSuite nor GHL is
configured, so a fresh checkout still renders. The banner now calls that
**"Sample data — a misconfiguration, not a mode"**, because that is what it means
once nothing can select it deliberately.

**What it costs, stated plainly.** The toggle existed because the walkthrough's
spine — an update arrives, the PM reviews it, publishes it, the homeowner sees it
— has no data on the real database. Measured just now: 9 real projects, contract
value and outstanding balance both a dash, **review queue empty, nothing
published**. **Steps 9–14 of the client walkthrough can no longer be
demonstrated**, only described.

The fix is one task for Sing: run `0001_hub_tables.sql`. `DEMO_HUD.md` now says
that instead of telling a presenter to flip a switch that does not exist.

**The HUD was actively wrong the moment this landed** — it instructed a presenter
to point at an amber "Demo data" banner and say "this screen is on demo data".
Corrected. While in there, two claims that had already gone stale independently:
a "189 automated tests" figure, and a backend note saying the dashboard runs on
fixtures, which stopped being true when `BuildSuiteDataSource` landed.

## On the tests

54 new, 389 total. Two things worth recording.

**The tests encode measurements, not guesses.** The Alliance shape (23 deals, 16
at draft ready, 0 matched, 0 signed), the age spread that justifies the bands,
the two budget vocabularies, the 9-projects-8-deals join — each is pinned to a
figure that came out of the database, with the date in the comment. When those
change, the tests should fail and be updated deliberately.

**The empty-tenant cases are not padding.** An empty funnel divides 0/0 for its
bar widths, which reaches a style attribute as `NaN` — and a browser treats that
as no width set, so the bar renders *full*. The screen would state the opposite
of the truth. That is a test that earns its place.

## Day 4 — the handoff path, and what it proves cannot work yet

*Written after the section above; day 4 landed later the same evening.*

What happens the moment a deal *is* signed, built now so the first one is not
spent debugging. The Hub half is finished. Building it found two blockers that
would otherwise have surfaced during the first real signature.

**WF1 had no trigger at all.** `RoutedWorkflow` listed WF2 through WF8 — the
router could not start WF1. A signed deal would have arrived, been verified,
routed nowhere and done nothing. Four event shapes route to it now, since GHL may
announce either the new record or the stage that produced it, and WF1 is
idempotent on the shared key so both landing is safe.

**The shared key rejects every project in the database.** §5 contracts
`buildsuite_project_id` as `BSP-YYYY-NNNNNN` and the validator enforces it. No
value in that format exists anywhere in BuildSuite:

| Candidate | Format | Populated |
|---|---|---|
| `projects.id` | UUID | **101 / 101** — and what `deals.source_project_id` points at |
| `projects.project_code` | `BSA-NNN` | 48 / 101, unique where present |
| `projects.award_code` | — | 0 / 101 |

Worth recording for C-3: **D4 §6 names the format `APS-081` and BuildSuite holds
`BSA-002`.** Three letters, a dash, digits — the same shape with a different
prefix. `project_code` is very likely what D4 meant, and nobody had looked at that
column. Added to `SOURCE-OF-TRUTH.md` as a second measurement.

**The mapping refuses rather than choosing.** §5 is a verbatim contract and the
key is open decision C-3; picking one here is exactly the reading error made
twice last week. So `buildHandoffFromDeal` fails precisely instead — it names the
field, quotes the value it had, and says whether the owner is BuildSuite or a
decision.

**A budget band is not a contract amount.** `contract_amount` must be a finite
number; BuildSuite has `budget_range`, a band, in two vocabularies.
`projects.exact_budget` exists and was null on every row sampled.

**The rehearsal replays the chain and reports where it stops.** Pure — no network,
no clock, no writes, and two runs are asserted identical. Steps 1–3 are
BuildSuite's and GoHighLevel's and are rehearsed as assertions about what must
arrive; a step we do not perform can never report `ok`. Steps 4–5 use the real
router and real planner.

Against live data: blocked at step 1 today because nothing is signed. Pretend it
signed and it blocks at step 2 naming both fields. Close the gaps and the Hub half
runs to completion — 17 effects, 7 milestones, 2 tasks, progress, portal access.

**One guardrail earned its keep:** `src/lib/handoff/` was not on the npm test
glob, so 18 tests would have looked like coverage and never run. The manifest test
failed, which is what it is for.

`docs/HANDOFF-CONTRACT.md` is the one-pager for Sing.
