## The whole loop rehearses

`rehearsal.ts` stopped at WF1 — a project exists. Today it carries on through the
part that has never run on anything real: a crew member submits an update, the PM
publishes it, the homeowner sees it.

Nine steps, **27 effects across three workflows**:

```
[theirs]  1. Signature captured in BuildSuite
[theirs]  2. Send-to-CRM assembles the §8.2 handoff
[theirs]  3. GoHighLevel creates the Project and fires a webhook
[ok]      4. The Hub routes the webhook to WF1
[ok]      5. WF1 plans the project                    17 effects
[ok]      6. The contractor sees it as signed work
[ok]      7. A crew member submits a field update     WF3 — 4 effects
[ok]      8. The PM approves and publishes it         WF4 — 6 effects
[ok]      9. The homeowner sees the published update
```

**It proves the negative, and that matters more than the happy path.** A
rehearsal that only walks forward proves the plumbing, not the product. The
invariant worth defending is the one that fails quietly: `Approved Internally` is
**not** approved for the client (§10). So step 8 runs the gate twice — once at
the internal status expecting refusal, once at `Approved & Published` expecting
it through — and step 9 also refuses a contact associated with a different
project (§1.4).

```
Privacy checks (§9.1 / §10):
  pass  "Approved Internally" is hidden from the client
  pass  "Approved & Published" reaches the client
  pass  a contact on another project is refused
```

**And the privacy block is load-bearing, not decorative.** Turning the §6.1
portal master switch off makes the published check fail, which makes the whole
chain report broken. There is a test for exactly that, because a guard nobody has
watched fail is a guard nobody knows works.

Pure like the handoff rehearsal — no network, no clock, no writes, and two runs
are asserted `deepEqual`. The privacy flags stay `false` when the chain never
reached them, so they cannot read as passed simply because nothing checked.

## The HUD was repaired, not updated

The plan said "update the HUD with the pipeline screen". What actually happened
is that rescraping the real screens found the HUD had drifted badly out of true.

**Five steps pointed at content that no longer exists**, on top of the demo-data
claims corrected yesterday. Worse: **four client-portal screens now scrape as
chrome only** — no title, no sections. A presenter following the old script would
have pointed at four blank pages, live, in front of a client.

That is not a scraper fault. It is accurate: the portal renders its empty state
because the Hub tables do not exist, and the previous maps had been scraped back
when the app still served fixtures. The maps were stale; reality had moved.

Those steps now say so and say what to talk about instead — the thirteen-section
navigation is real and is worth showing, and the two-audiences argument survives
being described. The instruction on the new pipeline step is explicitly **not to
soften the numbers**.

## Three scraper bugs, all the same species

`build-wireframes.mjs` exists because hand-drawn screen maps go stale. It had
three ways of going stale itself.

**`NAV_HREFS` is a hand-maintained list inside that script.** `/dashboard/pipeline`
shipped without being added, so every wireframe silently lost a nav item — the
exact class of error the file was written to prevent. Fixed, and it now warns
loudly on every run when a top-level app link is not on the list.

**The project-detail path hardcoded `BSP-2026-000184`**, a fixture id that only
resolved while the session was the fixtures' invented profile. It resolves a real
id from the live projects list now.

**`mint-cookies.mjs` still minted that fixture profile**, so maps were being
scraped under a tenant the real app never serves. Pointed at the real Alliance
profiles.
