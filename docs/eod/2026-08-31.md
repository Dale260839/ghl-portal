The brief was to make the system usable by real contractors: edit, update and

All three are built and running against live data. Two things found along the

## The two findings

### 1. A job has been signed. I had been saying none ever had.

For three days I reported **"0 of 182 signed"**. That was measured against
`deals.signature_signed_at`, a column BuildSuite does not populate. **Signature
lives on `proposals`:**

| | |
|---|---|
| `proposals` rows | 46 |
| draft / submitted / accepted | 27 / 15 / **4** |
| `signature_status = 'SIGNED'` | **4** |
| with `adobe_agreement_id` and `signed_pdf_url` | **4** |
| with a real `contractor_id` | 17 |

Four proposals signed in February 2026, all on one project. So the honest line is
*one job has been signed, once* — not *nothing ever has*. It also confirms the
matching work: the contractor link is `proposals.contractor_id` (34 of 46), not
`deals.matched_contractor_id` (5).

Corrected in `SYSTEM-STATE.md`. The older EODs are left as written, because a
record that quietly edits itself is worth less than one that shows its
corrections.

### 2. A cross-tenant leak, found by looking at the screen as two people

The new Active Work screen rendered identically for two different contractors —
both saw all seven live engagements, prices included.

`proposals` carries no `auth_profile_id`. Every other BuildSuite table the Hub
reads does, so "pass the scope and it is filtered" held everywhere until this
table. Here the scope only **asserted**; it did not filter.

This is the same shape as the August finding of 43 projects across five
contractors visible to anyone signed in.

**Fixed:** the tenant key for proposals is the contractor, and a session must be
resolved to one before anything is shown. `listLive` now requires a contractor id
and throws on an empty one rather than defaulting — `contractor_id=eq.` is a
valid filter matching the empty string, so that failure would have looked like
"no work" instead of "no filter", which is the worst kind because it looks fine.

**When the contractor cannot be resolved, the answer is nothing, not
everything.** Verified as two tenants: Alliance, unlinked, now sees an empty
screen with an explanation; Ralph, whose profile is the one linked to a
contractor, sees exactly his one signed job.

## What a contractor can now do

**See only work that has a deal.** `/dashboard/engagements` — jobs with a live
proposal, signed first, contractor-scoped. Enquiries with no proposal are listed
separately at the bottom rather than hidden, because a project someone cannot
find looks like a project the system lost.

**Edit and archive.** Every edit writes an **overlay** in the Hub's database and
never touches BuildSuite. Each field shows what BuildSuite holds underneath, so
clearing a box reads as "stop overriding this" rather than "delete the data" — a
null override and an empty string mean different things and there is a test for
it.

**Find what they archived.** `/dashboard/archive` lists everything archived
across all seven record types plus projects, most recent first, restorable in one
click and attributed. Archiving without that screen is a delete with extra steps.

**Invite their crew and their clients.** `/dashboard/team` — email, role, tick
what they see, revoke. The invitee follows a single-use link and sets a password.

## The decisions worth reviewing

**The Hub has its own database.** A separate Supabase project, so BuildSuite
stays read-only forever and nobody needs write access to someone else's
production data. Two clients: `BuildSuiteClient` has no write method at all;
`HubClient` writes and has **no delete method at all**.

**Archive, never delete.** `archived_at` plus who and why. The approval model
rests on being able to say who published what, and a deleted row destroys that
evidence.

**Effective permission = role AND grant. Never OR.** The role is the ceiling; a
tick can only lower it. Tested from the dangerous direction — a grant row saying
`invoice: true` for a client is still refused, because the role decides.

**Access is re-read per request, not cached in the session.** A session lasts
eight hours; if grants lived in the cookie, "revoke" would mean "revoke
tomorrow". An unreachable Hub database fails **closed**.

**RLS is off on the Hub database**, at your instruction, so policy-writing did
not block the build. Two guardrails are therefore load-bearing and both are
tested: the key is server-only and never `NEXT_PUBLIC_`, and exactly one module
reads it. The re-enable statements sit in `0002_rls_development.sql`. **This
needs closing before a real contractor's data lands there.**

## Two things I decided without you, and would undo on a word

**Invitation emails have no sender.** The link is shown once to the contractor to
send themselves. That is not a stopgap that leaks a secret — it is the same link
the email would carry, handed to the person allowed to create it. The seam is
there for GoHighLevel whenever you choose.

**A contractor can invite field and client, never another contractor.** Minting
another contractor felt like an account-level decision rather than a team one.

## Bugs caught, and by what

**Invited users could not log in again.** They set a password and `signIn` only
knew the demo identities, so an invitation was a one-shot session. Found by
asking what happens on day two.

**The two sign-in paths collided.** The demo radios and the new typed email were
both named `email`, so a selected radio shadowed what someone typed — they would
have been signed in as a demo identity while believing they used their own
credentials.

**Every invite token looked expired.** `readInviteToken` takes epoch seconds and
I passed milliseconds. Caught by its own tests.

**The guardrail bit three times** and each time it was taught rather than
weakened: new actions delegate `assertCan` to a helper, so the rule now accepts a
named delegate *and* separately asserts the delegate itself checks. Adding a name
to that list cannot become a way to opt out.

---

## Blocked, in the order that matters

**`auth_profiles.contractor_id` is populated on 1 of 110 profiles.** Until it is
backfilled, most sign-ins open Active Work to an explanation rather than their
work. Email matches 52 of 483 contractors, so a backfill is feasible. It is a
write to a BuildSuite table, so it is **Sing's, and it is the highest-value thing
on his list.**

**The one signed project is RLS-hidden from our key**, so its name and address
cannot be shown. The engagement is displayed anyway — dropping it would hide the
only real job in the system because of a permissions setting.

**A second signed job.** Not ours, and still the thing that gates the most.

**The shared key, the object key, the webhook secret** — unchanged, and detailed
in `docs/asks/`.
