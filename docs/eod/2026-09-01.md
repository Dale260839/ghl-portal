## The four-round failure, in order

You accepted an invitation as Dale and hit a server error. Each round below
begins where the previous one left you.

### Round 1 — the session had no tenant

`signIn` set `authProfileIds` on the session. `acceptInvitation` did not. So
accepting an invitation minted a session with no tenant, and the first scoped
read refused:

```
TenancyError: refusing an unscoped read of contractor identity
```

The refusal was correct. The session should never have been mintable that way.
Two functions built the same object by hand and drifted.

**Fixed**, plus a guardrail asserting every `setSession` call site carries the
profiles.

### Round 2 — the field interface had never worked on live data

Found while verifying round 1, not reported by you. `projectsForField` matched:

```ts
project.superintendent === fieldUser   // a name
```

Two things wrong. It is a §3.6 violation on its own — never match records by
name. And `superintendent` is `''` on **every** live BuildSuite row, so no crew
member would ever have seen a single project.

It had tests. The tests used fixtures where that field happened to be populated.
A test that only exercises the shape you imagined is not coverage.

**Fixed** — access now keys on the ids of projects a person holds a task on.

### Round 3 — an invitation granted nothing

Access came from tasks, and a freshly invited person holds none. Underneath
that: **nothing had ever written `hub_memberships.project_ids`.** The column
existed, `invite` took the parameter, the action passed `[]`.

The client half was worse because it was silent. `acceptInvitation` put the
**membership id** into `session.contactId`, and the portal looked that up as a
GoHighLevel contact id. It matched nothing, so an invited homeowner would sign
in successfully and read *"no projects are associated with this account."*

**Fixed**, and this is where the actual feature landed:

- the invite form asks **which projects**, not only which permissions
- existing members can be **reassigned** — without it, assignment could only be
  set at the instant of invitation, leaving everyone invited before today
  permanently stuck at zero with no way to correct it
- `setProjects` filters on the asserted contractor as well as the membership id,
  so knowing an id is not enough to reassign another contractor's crew
- the invited-client read is constrained **by construction**: `listProjectsByIds`
  returns empty for an empty list rather than dropping the filter, and no scope
  was widened to make it work — an invited client still inherits no auth
  profiles, so there is no scope with which they could over-read

### Round 4 — twice, because I fixed half of it

You signed in and hit a second error. `assertScope` requires a non-blank
`locationId` — correctly, since a blank tenant filter is a missing one wearing a
disguise. But a session only ever got its location from a **GoHighLevel**
sign-in, and an invited person does not have one:

```
{ locationId: '', authProfileIds: ['7726102a…'] }
```

The location was never a missing fact — it sits on the auth profile the member
already inherits. I made `requireTenantScope` read it from there.

**That fixed the pages and left every server action broken.** Six call sites
built a scope by hand from `session.ghlLocationId`. So the field interface
loaded, and then failed at the one thing it exists to do:

```
TenancyError: refusing an unscoped read of submit update
```

**Fixed properly this time.** `tenantScopeFor` is now the only place a scope is
built from a session, with two callers: `requireTenantScope` redirects for
pages, `actionTenantScope` throws for actions — a silent redirect mid-write
looks like the write succeeded.

## What I got wrong, plainly

**I fixed symptoms three times before fixing the cause.** Rounds 1, 2 and 4a
each addressed the thing in front of me without asking who else did the same
thing. Round 4 in particular: I repaired one scope builder while five others sat
in the same file, and you found the result.

**One of my guardrail tests was silently vacuous.** A shell-escaping slip put a
literal `0x08` byte inside a regex, so `/\.superintendent\b/` became
`/\.superintendent<BACKSPACE>/` — matching nothing while reporting green. I only
caught it because I reintroduced the bug to check.

**Every source-scanning guardrail written today was then verified by
reintroducing the bug and watching it fail.** A guardrail you have never seen
fail is not evidence of anything. That is now the rule for this repo.

**I told you to check your inbox for an invitation whose link I had hardcoded
as `TEST-LINK-NOT-REAL`,** without saying it was a placeholder.
