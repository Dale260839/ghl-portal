## 2 · The invoice flow — what the data actually supports

This is the substantive finding of the day, and it reshapes Next Step 1.

**There is no payment schedule table.** I probed for one:
`payment_schedules`, `payment_schedule`, `proposal_payment_schedule`,
`proposal_line_items` — all 404. The schedule lives inside `proposals.content`
as **markdown prose**. `proposals.sections` is null on every row in the
database.

### Three line shapes occur, not one

The handoff describes a line as title + percent + dollar amount + description —
*"Contract Signing, Scheduling & Permit Start, 30%, $25,434.00"*. That shape is
real but it is the minority. Verbatim from live proposals:

```
- **50%** upon acceptance of this contract and project scheduling
- Contract Signing (10%)
- **Contract Signing & Scheduling** (30% — $1,773.75)
```

Only the third gives all three. The first gives no title and no money.

### What the parser extracts, measured across all 46 proposals

| | |
|---|---|
| Proposals with a parseable schedule | **37 of 46** |
| Schedule lines extracted | **125** |
| …carrying a percent | **125** — all of them |
| …carrying a title | 47 |
| …carrying a dollar amount | 35 |
| Schedules **not** summing to 100% | **0** |

That last row is the one I trust the parse on. Passing my own fixtures proves
nothing; 37 independent schedules each summing to exactly 100% is a check the
data had to agree to.

### The finding that gates the pilot

For **all four SIGNED proposals** — the exact path a pilot would run — the
deposit draft comes out:

```
title = null    percent = 50    amount = null    source = unavailable
```

There is nothing to compute against. `proposals.total` is **null on all four**,
and `proposals.price` is a band string — `"$2,000 - $5,000"` — not a figure.

**So the draft never invents money.** Stated amount, else percent × contract
total, else **null — explicitly not zero**. Zero is a figure a contractor could
send to a homeowner by accident; blank is the honest representation of "we do
not know".

**This is not a degraded path.** Chris's own rule is that the contractor catches
a blank schedule at the review step. The data means that step is where the
invoice actually gets its numbers — it is the product, not a formality.

### Built and pushed

`lib/payment-schedule.ts` — parses all three shapes; `draftInvoiceFor` derives a
draft and reports what a person still has to supply; `paymentScheduleDrafts`
returns **every** line, because the handoff is explicit that this must not
hardcode "first line only" — each later line becomes its own invoice at its
milestone.

16 tests, fixtures copied verbatim from live proposals rather than invented.

## 3 · The git auth failure

Mid-afternoon every push began failing with `Invalid username or token`, then
hanging on a credential prompt that cannot be answered from a non-interactive
shell. Pushes had been working for hours before that.

Diagnosed: helper is `manager` (GCM), configured **at the repo level rather than
globally**, and **no `credential.credentialStore` is set** — so GCM has nowhere
durable to keep anything between sessions. No `~/.git-credentials`, no
`GITHUB_TOKEN`, no entry I could see in Windows Credential Manager.

Resolved by starting the push in the background so GCM could raise its own
sign-in window. Both remotes are level.

**It will recur.** One command fixes it permanently:

```bash
git config --global credential.credentialStore wincredman
```

I stopped short of enumerating the credential store — the sandbox blocked that
command, which is the correct behaviour for it, and I did not route around it.
