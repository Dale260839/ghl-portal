## 4 · The security review, and the defect it found

Reviewed the surface added this week: the sign-in door, the limiter, the email
sender, the webhook verifier, the rail.

### The finding — an ambiguous failure could invoice a homeowner twice

The rail reported `created: false` on three paths where GoHighLevel may
**already have created the invoice**: a 2xx whose body we cannot parse, a 2xx
carrying no id, and a connection dropped after the request lands. A 5xx is the
same class.

Reported as a plain failure, the contractor clicks again — and the second click
creates a real second invoice for the same instalment. That is precisely what
the unique index exists to prevent, **except the index cannot help when there is
no id to record.**

The result type now separates "definitely not created" from "cannot confirm". An
uncertain result tells the contractor the invoice may exist and to check GHL
before retrying, never retried on their behalf. A 4xx stays a clean refusal,
because nothing was written.

### What came back clean

- No database key is `NEXT_PUBLIC_`, and a test already enforces it
- The dev console sender prints the sign-in link and is **double-guarded**
  against production — the resolver picks a failing sender there, and the
  console sender refuses on its own as well
- The limiter keys on email and IP, **never the project code**, so the small
  code space cannot be walked
- Webhook signatures use `timingSafeEqual`
- Rail errors summarise rather than echo, so a token in a header cannot reach a
  log through an error
- `invoice` is contractor-only in the matrix and **not grantable**, so a tick
  cannot widen it
