## 2 · Exact pricing, and the signed contract

**`price` holds two shapes and only two** across all 48 rows: 33 a single number
(`"24500.00"`), 15 a band (`"$2,000 - $5,000"`). So it is now parsed — but only
when the **whole string** is one number. A band contains a hyphen and cannot
match, so it falls through rather than being read as its low end, which would
quote a homeowner $2,000 for a job that might cost $5,000.

Exact-price coverage went from **10 of 48 to 33**.

The Projects screen showed a range in a column headed Contract even on the
signed job. Four states now render differently:

| basis | meaning |
|---|---|
| **contract** | from a signed proposal — the figure the invoices are built from |
| **quoted** | real, but nobody signed it. Shown, and labelled |
| **range** | the band, marked "estimated range" |
| **none** | a dash, never `$0.00` |

Live: 1 contract, 5 quoted, 24 range, 3 none. `flooring` was **blank** and is
$34,400.

**Revenue Under Contract** on the Portfolio Dashboard read `—` because it summed
`currentProjectTotal`, which is `0` on every live row. It now sums **signed
proposals only**, one per project so a job with several is not double-counted:
$24,500.

### Two corrections from Sing, both real

**The signed PDF URL is public and unauthenticated.** Anyone holding it opens
the client's contract, prices and address included. I had put that link on two
screens knowing only that it existed. It is now linked only from behind the
contractor login, every link carries `rel="noreferrer"`, and two guardrails fail
if it reaches a portal screen or an email — both verified by reintroducing the
violation.

**One row stores the literal string `"null"`.** Four characters, not SQL NULL,
on `027b2b2f`. Our check was "non-empty", so the screen rendered
`<a href="null">Signed contract</a>` — a dead link labelled as the contract,
which reads as a missing document rather than an absent one. A value must now
look like an `http(s)` URL to be linked at all.

I also misread the ask twice: *"add this column in the projects table"* meant a
**UI column on the Projects screen**, and I read it as a database column, argued

## 3 · Four confirmations — and two that were not true

Asked to confirm four client-privacy guarantees. I confirmed them by **breaking
each and watching a test fail**, which is the only reason I caught this:

**Two of the four passed their tests and were not actually enforced.**

*The approval clause had never been tested.* Every unapproved fixture also has
`clientVisible: false`, so the two conditions are perfectly confounded — clause
one denied everything before clause two was consulted. **I deleted the entire
approval check and the suite stayed green.**

*The summary test checked shape, not value.* It asserted the four key names, so
publishing `workCompleted` as `clientSummary` kept the same keys and passed — a
test named "carry the summary and never the work log" that never looked at the
work log.

Both fixed. All seven violations now caught: internal notes reaching a client,
approval skipped, work log published as the summary, cross-project access, the
portal master ignored, and either date fabricated.

Storage structure was also decided and written down —
`hub-media/<contractor>/<project>/{photos,documents}/<uuid>-<name>`, private
bucket, signed URLs at 600s. Contractor first so policies are a prefix match
when RLS returns.

## 4 · Six screens were shells. Four are real now.

You spotted it: Schedule, Milestones, Designs & Selections, Change Orders,
Documents, Photos — screens that existed and did nothing. Confirmed before
building:

```
SCREEN                FORMS  ACTIONS  READS
Schedule                0      none   portal-fixtures
Milestones              0      none   live, read-only
Designs & Selections    0      none   portal-fixtures
Change Orders           0      none   portal-fixtures
Documents               0      none   portal-fixtures
Photos & Videos         0      none   portal-fixtures
```

Zero forms, zero actions between them. Every "New appointment" / "Add milestone"
/ "Upload" button was a `<button type="button">` with no handler — the component
comment literally said *"Not wired."*

### Built today

**Schedule** — `hub_schedule_items` had existed since 0001 and nothing had ever
touched it. Create, edit, release, archive.

**Milestones** — `createMilestone` existed and nothing called it. Added
`updateMilestone` and `archiveMilestone`; the screen now adds, edits, reorders,
sets status, releases and archives.

**Documents and Photos** — one module for both, because the tables differ by two
columns and everything that matters is identical. Two copies would be the same
rules written twice, and the second is the one that drifts.

The bug worth naming: **`storage.ts` could already put a file in the bucket, and
nothing ever wrote the row saying which project it belonged to.** An uploaded
file was unreachable. Upload now happens first and the row carries the returned
path, so a failed upload leaves no row pointing at nothing.

Files serve through a new `/api/files` route minting a short-lived signed URL
after establishing the caller owns the path. Removal archives the **row** and
leaves the object — deleting it would break any signed URL already issued.

### On permissions, which is what you asked

**The field inspector already cannot reach any of these screens.** `/dashboard`
redirects any session that is not a contractor. I did **not** change the
permission matrix to strip field read — the route guard already does the job,
and the matrix is a §-referenced contract.

Three gates on every write: the route, `assertCan`, and the tenant filter on the
query. Client visibility needs both the row's flag and the project switch, and
each screen shows both so a contractor can see what the homeowner actually gets.

### The guardrail caught me again

`signedFileUrl` was an exported server action that never called `assertCan`. It
was a read, so an exemption was tempting. The honest fix was noticing
`/api/files` already did that job and nothing called the action. **Deleted
rather than excused.**
