## 1 · The homeowner login is now the project code

Chris's decision: when the contractor and homeowner sign, a BuildSuite
automation emails the homeowner their project code, and **that code is their
password**. The email on the contract is their username. Nobody invites them and
nothing expires in between.

**Invitations are now field crew only.** `INVITABLE_ROLES` is `['field']`, so a
contractor cannot hand-create a homeowner account at all.

I flagged the obvious problem before building it, because I had written the
warning myself in `client-lookup.ts` some days earlier:

> The code space is small … That is acceptable ONLY because this mints nothing …
> **If this ever issues a session directly, the code is not enough.**

Codes run `BSA-001`–`BSA-055`, sequential — about six bits. That paragraph is
still in the file, unsoftened, because it is the reason the new door carries:

- **a signature gate** — an unsigned project's code opens nothing, ever;
- **five attempts an hour**, keyed on the email and the IP, never on the code;
- **no stored hash** — the code is checked live against BuildSuite, so
  `hub_memberships` holds no client credential to crack.

Verified against live data:

```
BSA-052      right email   -> signed-in
BSA-APS-001  right email   -> signed-in     (typed lowercase, still works)
BSA-044      right email   -> rejected      (contract unsigned)
BSA-052      wrong email   -> rejected
injection in either half   -> rejected
six guesses in a row       -> rate_limited
```

**I also retired the emailed sign-in link.** It required no signature and minted
a `contactId` session that returns *every* project a contact holds. Leaving it
wired would have made the new gate decorative.

**Two steps remain untested:** the `hub_memberships` insert and the cookie →
portal render. Both need one real sign-in, which is a write to a live table, so
I stopped and asked rather than doing it.

## 2 · Then you gave me six tasks. All six are done.

### Project numbering — a convention, not a note

Two series, both allocated inside BuildSuite:

```
BSA-NNN       54 codes, 1–55, spread across SEVENTEEN owning auth profiles
BSA-XXX-NNN    2 codes, one per-contractor counter behind a chosen prefix
```

Zero duplicates. **The whole string is unique; the number is not** — `BSA-002`
and `BSA-APS-002` are different projects, as are `BSA-001` and `BSA-APS-001`.
Two independent counters will collide on the suffix forever, so nothing may key,
sort or display on it.

Encoded in `packages/contracts`, not just written down, with
`projectCodeSeries()` and `projectCodePrefix()` so nothing parses a code itself.
`npm run check:codes` verifies it against live data and exits non-zero on a
violation.

**The real collision risk is the prefix**, which is *chosen*, not allocated. Two
contractors both shortening to `APS` would mint the same code from two counters.
Nothing in BuildSuite prevents that; the checker reports a shared prefix before
it becomes one, and the sign-in already fails closed.

### Files: duplication and per-project access — and a live bug

Eighteen cases across both the row and the bucket object, because access has to
hold in both. Then, tracing how a client reaches a file, this:

> **Eleven of the fourteen portal screens showed every homeowner "No project".**

`currentPortalProject` resolved a client only through
`listProjectsForContact(session.contactId)`, guarded by `contactId !==
undefined`. That handles one of the two kinds of homeowner. Since the code
sign-in deliberately mints no contact id, it is now **every** homeowner —
Documents, Photos, Schedule, Budget, Timeline, Updates, Issues, Messages,
Designs, Change Orders and Completion all empty. Only the home page, the layout
and Payments went through `clientProjectsFor` and worked.

Silent, and it reads as *"your contractor hasn't shared anything yet"* rather
than as a fault. **No test was failing.** I found it by following the path.

Fixed, and pinned by a guardrail — which then needed a second pass of its own,
because it first matched the comment that *names* the old call while explaining
the bug, and failed on correct code. Guardrails that assert a call is or is not
made now strip comments first.

### The full journey, as one record

`publishing.test.ts` already covered the pieces. Nothing covered the **seam** —
one update carried the whole distance with the permission matrix consulted at
each step and the §9.1 gate run on the object the field user actually filed.

```
field files it          -> Pending, PM notified, client sees NOTHING
field tries to publish  -> no field actor exists on any approval edge
PM returns it, refiled  -> still nothing
PM approves INTERNALLY  -> WF4 skipped, client STILL sees nothing
PM writes the summary   -> editing does not advance the state
PM publishes            -> WF4 fires, client notified once
what arrives            -> four keys, none of them the field notes
```

The leak check is **by value**, not by field name — which is what a leak
actually looks like when a projection copies the wrong field. Verified by
reintroducing four separate leaks.

### Milestones and tasks — a second live bug

`createMilestone` writes `planned_start`/`planned_end`. `updateMilestone` wrote
`target_date`/`completed_date` — the pair migration 0001 created and 0003
superseded. Create was updated; edit was not.

So a PM edits a milestone's dates, saves, and the old dates come back. The save
wrote a row, just not to the columns anyone reads. **The half that survives a
refresh is worse:** the end date landed in `completed_date`, giving a milestone
nobody had finished a completion date. See §6 — this one bit.

Also reviewed and deliberately **not** changed: milestone status has no
vocabulary anywhere. §6.3 gives the task enum verbatim; §6.2 says
`Status (select)` and never lists the values. That is a §16 open decision and
CLAUDE.md says not to pick a sensible default, so I have not.

### Hub ↔ GoHighLevel messaging, documented

The finding worth reading:

> **`NotifyClient` only logs.** A PM publishes, WF4 fires correctly, the portal
> updates — and the homeowner is not emailed. The terminal prints
> `[workflow] NotifyClient — …` and that is all.

Honest scaffolding, and `fixture-ports.ts` says so. But nothing in the UI tells
the contractor, who will reasonably read the silence as the homeowner ignoring
them. Closing it is a `ghlPorts` module implementing the same `EffectHandlers`
type — the workflows do not change, which is what the port boundary is for.

Portal messaging is not wired either: fixtures, and Send/Reply are
`type="button"` with no handler. Both visibility switches work, so the gate is
real and the transport does not exist.

## 5 · What I got wrong today

**I claimed no live data was affected by the milestone bug.** I wrote that in
the review, from the code and the migrations, and it was wrong. §6 is the
correction. The method point is worth keeping: reading the code was enough to
*find* the bug and not enough to know whether it had *bitten*. Only the rows
could say, and they said the opposite of what I assumed.

**One of my own new tests passed for the wrong reason.** "An unsigned project
admits nobody" used a contractor lookup that refused anyway, so it stayed green
when I deleted the signature gate entirely — it was refusing, just not for the
reason the test claimed. Caught by reintroducing the bug, then strengthened so
only the gate can make it pass. Same lesson as the two vacuous guardrails last
