## 4 · Two things I got wrong, both found by reading their work

### 4.1 My migration 0009 broke two live screens

`0009_selections_change_orders.sql` created `hub_selections` and
`hub_change_orders` **and enabled row level security on both, with no
policies.** Every other Hub table has RLS disabled, because the app reaches the
Hub with a key RLS applies to.

The effect on the APS pilot project, from their note, seen 10 Sep:

> both screens rendered, both lists were always empty, and every Add silently
> failed with a row-level-security refusal

**Silent** is the word that matters. A contractor adding a change order got no
error — the form submitted and the row simply was not there. Nothing was lost
because nothing was ever written, but anyone using those screens for the last
day has been talking to a wall.

I wrote that migration and did not check what it did to a table it had just
created. `0011` undoes it. **It needs running today.**

### 4.2 My messaging doc said a table did not exist. It has existed since 0001.

Yesterday I wrote, in `MESSAGING-HUB-AND-GHL.md` §6:

> There is **no `hub_messages` table** and no write path anywhere.

The second half was true. The first half was wrong — `hub_messages` has been in
migration 0001 from the beginning, with `client_visible` defaulting to false and
a comment already stating the rule it exists to keep: *a crew↔PM thread must
never surface to a homeowner.*

Corrected today. A document that says a thing does not exist is how a second one
gets built beside it.

**And the §16 decision that section posed has been answered** — where messaging
lives. I listed GoHighLevel conversations and a Hub table, declined to choose,
and they chose the Hub table. The trade-off I named still holds: the
conversation now lives in two systems, which is the thing the invitation email
was routed through GHL specifically to avoid. Worth revisiting if homeowners
start replying to Hub notifications by email; not worth re-opening now.

## 5 · `0010` is loaded, and the secret rotation now gates it

Their migration re-enables RLS on every Hub table. The warning on it is correct
and worth repeating here, because it turns a chore into a dependency:

> RLS only bites a non-service key, so `HUB_SUPABASE_KEY` on the deployment IS
> the anon key today. Running this file before swapping that key would take the
> whole Hub down.

So the order is fixed and cannot be shuffled:

1. Confirm which key `HUB_SUPABASE_KEY` is (the JWT `role` claim says).
2. If it is anon, **swap it for `service_role` first**, redeploy, verify one
   screen saves.
3. *Then* run `0010`.
4. `0011` is independent and should go **now** — it undoes my 0009 accident.

The secret rotation has been an item on the list since 31 August. It is no
longer just hygiene; `0010` is waiting behind it, and `0010` is what stops
anyone holding the anon key from reading every contractor's rows.
