## 1 · What GoHighLevel refused, and what it allowed

Four hard constraints, all measured against the live Marketplace, none of them
in any documentation I could find first:

| | |
|---|---|
| A redirect URL containing `ghl` | Refused on a white-labelled app. Our routes are `/api/connect/*` because of it. |
| Contacts, conversations, invoices on an **agency** app | Greyed out: *"This scope works with Location-level tokens only, which are issued when a Sub-Account installs your app."* |
| A **paid** app installed from an external link | Refused — and pricing cannot be edited once a version is published. |
| `marketplace.gohighlevel.com` | Asks for a HighLevel login that a contractor in a white-labelled agency has never had. |

And the one thing it does allow, which is the whole answer: **`locations.readonly`
is available to an agency app**, badged "Sub + agency". Sign-in makes exactly one
call, `GET /locations/{id}`. So an agency install can prove every sub-account,
while the sub-account app does the work that needs location-level scopes.

## 2 · Two apps, and what each one buys — `c19e644`, `d88aaea`, `f554079`

**The sub-account app** holds contacts, conversations and invoices. You install
it from Agency → App Marketplace across all sub-accounts in one action. That
grants the scopes everywhere but sends no OAuth redirect per location, so there
is no per-sub-account row to store — the Hub mints one on demand from the
agency's own token for the same app (`POST /oauth/locationToken`).

**The agency app** holds one scope and stays that way. One install proves every
sub-account, so a contractor who has installed nothing signs in anyway, and sees
everything that comes from BuildSuite — which is nearly all of it.

Together: **a contractor opens Project Hub from their menu and is signed in as
themselves, with invoices and email working, having done nothing.**

Credentials resolve in one place, most specific first: the sub-account's own
install, then the agency install, then its Private Integration token. The PIT
path is untouched and still decides when the others cannot.

## 3 · The dead end became the way in — `4f06fd7`, `c63111f`

A brand-new sub-account's menu link answered *"That link doesn't match a
sub-account we have access to"*, with nowhere to go. Proving a sub-account needs
a credential for it, and the credential was the thing they were missing.

So `/connect` stands **in front of** sign-in rather than behind it, and that
failure now lands there. It is the sign-in page's twin — same layout, same
pitch, same navy — because they are the two front doors to the same product. It
reads nothing at all: no database, no BuildSuite, no session, only the
sub-account id already in the visitor's URL. A guardrail keeps it that way.

## 4 · Who clicks, and where — `207b1fc`, `cd828d8`, then corrected

The prompt to connect moved from *"an admin creates a token, copies it into the
deployment and redeploys"* to a one-click prompt in the product.

Then **John caught the flaw in making it automatic**: the approval screen lives
on `marketplace.gohighlevel.com`, and a contractor in a white-labelled agency
signs in at the agency's own domain. Redirecting them lands on a login they have
never had — a dead end dressed as a button, worse than the honest one it
replaced. So the automatic redirect is now opt-in and off, and every screen
leads with the route that works for them: the App Marketplace **inside their own
account**, which uses the session they already have.

## 5 · What I checked, and what I did not

from here twice by fetching public pages — `/connect` renders live, and

**Five breaks were missed on the first attempt**, and every one taught something:

**Not checked:** whether the agency token can read a sub-account that never

## 8 · The thing worth keeping

Today's design was not chosen. It was what was left after GoHighLevel said no
four times, and each no arrived as a screenshot of an error rather than as
documentation. The plan written yesterday was wrong by lunchtime, and the
version that works is simpler than the one that did not.

The part worth remembering is that **the flaw in the automatic redirect was
spotted by the person who knows the accounts, not by the tests**. Nothing failing
in CI could have told us that contractors do not have a HighLevel login. That is
the second time this week the useful bug came from somebody imagining a real
person trying to use the product.
