# Project Hub — the update survives the site

**26 September 2026** · written to be sent to Chris
**Live at:** https://project-hub-one-vert.vercel.app

---

## Where the app is actually used

A daily update is five fields of typing, done one-handed, on a phone, at the end
of a physical day — on a roof, in a basement, in a truck, by the least patient
person in the system with the worst connection of anyone who touches this.

Until today the app assumed the signal held and the page stayed open. Three
things happened when it didn't, and all three are fixed.

## A photograph could go missing from its own update

Yesterday we made a photograph belong to the update it was sent with. What we
missed: nothing stopped a crew member pressing **Send update** while a photo was
still going up. That photo was never attached — it survived on the project's
Photos page and was missing from the one place it was taken for.

On a site with one bar that isn't a rare case, it's the normal one. **This was
our defect, shipped yesterday, found and fixed today.**

The send button now waits, and says what for: *"2 photos still uploading…"*.

## A failed photo is no longer the end of it

A photo that fails now tries again by itself — three times, pausing a little
longer each time. If it still won't go, it says so and offers a **Retry**,
rather than a tile that quietly sits there looking wrong.

And the crew member is never trapped. **Waiting is only for photos still in
flight, never for one that has given up.** Somebody in a basement with no signal
can still file their day's work, and is told plainly which photograph isn't
going with it — rather than finding out afterwards.

## Twenty minutes of typing can't be lost any more

A call arriving, a flat battery, a failed send — any of them used to lose the
whole update.

What they type is now kept on their own phone as they type it, and offered back
when they return: *"You started an update and did not send it."* With the time,
and one tap to discard.

It asks rather than restoring silently, because yesterday's text appearing
unannounced in today's form is worse than an empty form — they'd file yesterday's
work as today's without noticing. And it's only cleared once the update is
actually filed, so a send that fails leaves every word where it was.

None of it leaves the phone.

## For us — the operational half

Not for sending.

**Shipped:** 1 commit · 9 files, +685 / −41 · 1,208 tests green (+10), typecheck
and build clean, both remotes level at `2dec946`.

**The gate is pure and tested on its own** — `lib/field-upload-state.ts`:
`countUploads`, `submitGate`, `retryDelayMs`, `shouldRetry`. Every message and
every decision is testable without a browser, a network or a photograph. The
rule that carries it: **in flight blocks, failed does not.** Both halves are
break-tested, because reversing either one is a plausible "tidy-up".

**Why a context, not a prop.** The uploader and the send button are separated by
the form's own markup, so threading state means every screen with an uploader
holds the wiring correctly — and the one that gets it wrong silently drops
photographs. Without a provider, nothing changes, which is what the task screen
wants.

**Retry keeps the shrunk blob** so it doesn't re-encode a photo that already
shrank fine; the manual Retry only appears once it has stopped trying on its
own, or it is two queues for one photo.

**The draft** is one key, not one per project (a crew member writes one update at
a time), includes the selected project, and is cleared by the Today screen on
`?submitted=1` — never by the form. Every read and write is wrapped: private
mode and full storage must not break typing.

**Guardrails added:** the ungated `SubmitButton` cannot come back to that form;
the provider must be present or the button hears nothing; the draft is not
cleared on the writing screen; a draft never posts anywhere. `FieldSubmit` is
now on the raw-submit-button exemption list, with the reason — it does more than
that rule asks, not less.

**Five deliberate breaks, all caught**, including both directions of the
in-flight/failed rule.

**Still ours, unblocked:** delete the PITs once contractors are proven on the new
path; `BLOCKERS.md` needs a full pass (four rows resolved days ago);
`lib/data/source.ts` still swaps location while keeping the default token —
harmless only because `GHL_PROJECT_OBJECT_KEY` is unset, so do not set that key
until it is fixed.
