## 1 · Project Hub went down this afternoon, and is back

Row-level security was switched on across all 35 BuildSuite tables today, and
the public key Project Hub had been reading with lost its privileges.

We measured it rather than assumed: **every table answered `401 permission
denied`** — projects, proposals, deals, contractors, auth profiles. Not empty
results, a hard refusal. The same key read 115 projects on Friday.

**Signing in broke first.** Opening the Hub resolves a GoHighLevel sub-account
through the auth profiles table, so no contractor could get in at all. What they
saw — "this sub-account has no BuildSuite projects linked yet" — is an honest
message for an entirely different problem, which is the worst kind of error to
be handed.

**Fixed the same afternoon** by moving those reads to the service key, held as a
server setting. Verified on production: a contractor signs in, awarded projects
list, BSA-052 [HUB TEST] fully populated including its signed proposal and
payment schedule, invoices load.

**No policy was added**, which was the thing Sing asked everyone not to do. The
fix needed nothing from his side. Our reply to him, with the measurements, is
`docs/replies/sing-2026-09-29-supabase-rls.md`.

Worth knowing: **nothing about that change was wrong.** Locking those tables
down was right, and we were relying on a key that should never have been able to
read them. The outage was the cost of finding that out.

## 2 · The operator controls were showing to everybody

Dale noticed two buttons in the top bar — **Switch account** and **Viewing as** —
and asked why anyone other than the Alliance For Contractors admin account had
them.

They were switched on by a setting, and a setting cannot tell one contractor
from another. That was fine when one agency used this. It stopped being fine the
moment 149 sub-accounts came online: **every contractor on every one of them
could see both.** The role switcher was the worse of the two, because it was on
by default.

They are now tied to the agency's own sub-account, and three things about that
are worth saying plainly:

- **The buttons being hidden is not the fix.** Both sit behind requests anyone
  could send by hand, so the refusal is on the server; hiding them is only the
  polite half.
- **The list of accounts is itself the client book.** It is other contractors'
  business names, so it is no longer built for anyone who is not entitled to it
  — not merely hidden after the fact.
- **Setting nothing gives the controls to nobody.** It does not fall back to
  "whoever is first" or "whoever this deployment belongs to". A default that
  guesses who the administrator is will eventually guess in somebody's favour.

## For us — the operational half

Not for sending.

**Shipped:** 3 commits · 11 files, +458 / −12 · 1,217 tests green (+9), typecheck
and build clean, both remotes level at `0578309`.

**The key.** `lib/buildsuite/client.ts` reads `SUPABASE_SERVICE_KEY` first and
falls back to `SUPABASE_ANON_KEY`, so the window between deploying and setting
the variable was uneventful. A key positively identified as anon now logs once,
naming the variable to set, rather than leaving somebody reading 401s. The
missing-variable message names the service key too — telling someone to set the
anon key would send them to a key that cannot read a row.

Safe because all three already existed: that client has no method but `GET` and
throws on a constructed write; it is `server-only`; and tenancy never depended on
RLS — every read is filtered by the signed-in contractor's own auth profile ids
in application code (D-012).

**The gate.** `lib/admin-access.ts`, keyed on the GoHighLevel sub-account from
`realIdentity` — so viewing-as does not revoke it, which would strand an admin
in the assumed view with no way back. Enforced in `viewAs`, `switchAccount`,
`listDevAccounts` and all three layouts.

**An existing §3.6 guardrail caught my `?? ''`** on the location id: a blank
tenant filter is no filter, and the rule is right even where the next line
refuses it. Fixed rather than exempted.

**Five deliberate breaks, all caught**, including an unset `ADMIN_LOCATION_IDS`
letting everyone in and another contractor being treated as the agency.

**Recorded so it does not bite twice:** a BuildSuite read that returns nothing or
401s is a **key** problem, not a data problem — check `SUPABASE_SERVICE_KEY`
before looking anywhere else. The same trap is waiting in n8n, House
Intelligence and anything else using the public key; those are Dale's to check
and Sing's note asks for a table.

**Still ours, unblocked:** delete the PITs once contractors are proven on the new
path; `BLOCKERS.md` needs a full pass; `lib/data/source.ts` still swaps location
while keeping the default token — harmless only because `GHL_PROJECT_OBJECT_KEY`
is unset, so do not set that key until it is fixed.
