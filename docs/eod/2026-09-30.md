# Project Hub — what an audit found

**30 September 2026** · written to be sent to Chris
**Live at:** https://project-hub-one-vert.vercel.app

---

Today was spent looking for problems rather than adding features: exposed
keys, ways in that should not exist, things a crew member or a homeowner could
reach that are not theirs, and any invented data still being shown as real. Six
things were found. Five are fixed and live; the sixth is written up because it
cannot be fixed cheaply and pretending otherwise would be worse.

---

## The one that had been wrong every day

**Your dashboard was showing change orders that do not exist.** The count of
open change orders, the money said to be **waiting on a client**, and part of
the activity feed were all read from a file of sample data left over from
before the database existed. Not as a fallback when something failed —
every time, for everyone.

The per-project Change Orders screen has always shown the real thing. That is
why this survived so long: the two screens disagreed, and nobody had reason to
put them side by side.

Now it reads the database. When the database cannot be reached it shows nothing,
because a number invented to fill a space on a screen is how somebody ends up
chasing a client about a change order that was never raised.

## What a crew member could reach

A crew member could open **any file belonging to their contractor** if they had
its link — including a signed contract with its pricing, files on jobs they were
never assigned to, and documents meant only for the homeowner.

Their own screens only ever showed them their own jobs. But a screen is a
display, not a lock, and this was a plain web address anyone could type.

It was never something you could stumble into — the links are long random
strings. The realistic case is quieter: **a link that keeps working after
somebody is taken off a job, or leaves.**

Now closed, both ways in. A refused file answers "not found" rather than "not
yours", because confirming that a document exists is itself telling somebody
something.

## The homeowner's password was in every email we sent them

A homeowner signs in with their email and their project code. That code is
their password — it never expires — and it was printed in the body of **every**
update, change-order and message notification. Forwardable, searchable, sitting
in an inbox for years.

It is out. The email now says where to find the code — on their contract, on
their invoices, and their contractor can resend it — which is a pointer rather
than a password.

This is a patch on a design we should still change: the right answer is a link
they tap instead of a code they type, and that remains the single biggest
improvement available on the client side.

## Two more, quietly

**The crew's Messages screen invented conversations** when it could not reach
the database. Yesterday a key was revoked and screens went blank for an
afternoon; had it been that database, a crew member would have read made-up
messages from their project manager and replied to them. It now shows nothing,
and says why.

**Uploads had no limit.** Anyone signed in could send 3.5 MB at a time, as often
as they liked, into storage you pay for. The realistic cause was never an
attacker — it is a crew member with poor signal tapping Retry twenty times, and
a bill arriving quietly a month later. Capped at sixty photos an hour per
person; nobody doing their job will ever see it.

## The one that stays open, and why

Sign-in links from GoHighLevel are not signed, so the address alone is what
gets somebody in. I said last week the cheap fix was to sign them. **I was
wrong**, and it is worth saying so plainly: the menu link is now one
agency-level link shared by all 149 sub-accounts, so there is nowhere to put a
signature that means anything.

The honest options are to go back to 149 separate links — undoing the zero-touch
onboarding built last week — or to do proper single sign-on, where GoHighLevel
vouches for who is arriving. **Single sign-on is the answer**, and it is the
same piece of work that would finally tell us *which person* at a contractor did
something, rather than only which company.

## For us — the operational half

Not for sending. Full findings: `docs/SECURITY-AUDIT-2026-09-30.md`.

**Shipped:** 2 commits · 20 files · 1,219 tests green (+2), typecheck and build
clean, both remotes level at `5a74120`.

**Clean on inspection:** no `.env` committed and no key in source (the only
`sb_secret_` hits are the prefix used to classify a key); no
`NEXT_PUBLIC_SUPABASE_*` and a test that fails the build if one appears; both
database clients `server-only`; cross-contractor storage closed by the
`contractorId/` prefix rule; the webhook signature-verified against the raw
body; BuildSuite structurally GET-only; no fixtures left under `app/portal/`.

**Fixes:** `listAllChangeOrders` + the dashboard; `fieldMaySee` / `fieldMayReachPath`
on `/api/files`; fixture thread removed from field Messages; `upload-limits.ts`
(60/hr uploads, 120/hr client writes, keyed on the person — a cost ceiling, in
memory per instance, and the file says so); the project code out of
`homeowner-email.ts` (`projectCode` no longer destructured, so nothing can
quietly reach for it); `lib/data/source.ts` now requires the location's own
token and falls through to BuildSuite without one.

**Guardrails added:** the file route's crew gate, pinned to the refusal that
uses it — my first version asked only whether `fieldMaySee` *appeared*, which
passes happily while the condition beside it says `false`, and two breaks sailed
through before I noticed. No screen under `app/field` or `app/portal` may import
fixtures at all — the class, not the instance. The per-location-token rule now
covers `lib/data/source.ts`, the one caller nobody had added to it.

**`GHL_PROJECT_OBJECT_KEY` is now safe to set**, which it was not this morning.

**Still ours, unblocked:** delete the PITs; `BLOCKERS.md` needs a pass (four
resolved rows still listed as open); the refinements in §4 of the audit — crew
messages merged across jobs, no read state on messages, portal photos ungrouped.
