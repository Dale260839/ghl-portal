# Project Hub — three releases, and the same wall three times

**6 October 2026**
**Live at:** https://project-hub-one-vert.vercel.app

---

## 1 · Signing out stopped failing after a deploy

Deploy the Hub while somebody is signed in and their next click could land on a
session the new build no longer recognised. The sign-out they reached for to
fix it was the thing that broke.

Sign-out is its own route now and clears the session whatever state it finds,
so the way out always works. The error screen beside it learned to recover a
broken workspace rather than stranding somebody on a dead page.

This is unglamorous and it is the difference between "the site is down" and "I
clicked sign out and went back in".

## 2 · A clock-skew error that looked like an outage

Reads from the Hub were intermittently refused with *JWT issued at future* —
the database rejecting a token whose timestamp sat a second or two ahead of its
own clock. Nothing was wrong with the data, the token or the user. It simply
looked like the Hub was down, at random, to one person at a time.

Those reads retry now. **Reads only** — a write that failed uncertainly may
already have committed, and retrying it is how one invoice becomes two.

## 3 · A dependency advisory, closed

`source-map-js` 1.2.1 → 1.2.2, a denial-of-service advisory in a transitive
dependency. Three lines of lockfile. Verified by reinstalling from the lockfile
and running the whole suite against it: **1,442 tests, zero vulnerabilities**.

## 4 · The wall, three times

Each of those three releases was merged, and each was **blocked by Vercel
before it could deploy**:

> The deployment was blocked because the commit author did not have
> contributing access to the project.

The Hobby plan does not support collaborators on a private repository, and
GitHub records whoever presses the merge button as the author. So every merge
made through the GitHub UI arrived authored by an account Vercel will not build
for — three times, for three unrelated changes, from one cause that had nothing
to do with any of them.

Each was unblocked by rewriting the merge's authorship and nothing else: tree
hashes identical, both parents intact, not a line of code different. The
reasoning is recorded in the merge messages rather than left to look like an
accident.

**This will happen again on the next merge made through GitHub.** There are
three ways out and they should be chosen deliberately:

| Option | Cost |
|---|---|
| Keep rewriting authorship after each merge | A manual step, every time, that someone must remember |
| Upgrade Vercel to Pro | A subscription, and the problem disappears |
| Merge locally rather than through GitHub's button | Free, but changes how the team works |

A second thing worth knowing: **a force-push does not reliably trigger a new
Vercel build.** Twice the authorship was corrected and nothing happened,
because from the outside the branch tip had merely changed rather than moved
forward. Each correction now carries a real commit behind it.

## 5 · The sign-in documentation described a door that no longer opens

Every instruction in it was for the old Custom Menu Link flow, which the
hardening release deliberately retired. Left as it was, the next person to set
this up would have followed a path that cannot work.

Rewritten around what actually runs, with the two findings worth never
rediscovering:

- A Custom Menu Link in **Embedded Page** mode is a real iframe with a trusted
  parent origin, and still never receives user context. Only a Marketplace
  **Custom Page** does.
- The agency id must never be transcribed by eye. The live value is
  `19WlZc8l7w03KWCJKK2E`, where the obvious reading of the lowercase `l` is a
  capital `I`. One wrong character refuses every sign-in.

## What is *not* done, honestly

**Contractor sign-in is still down.** The configuration it needs —
`GHL_SSO_COMPANY_ID` — has not been confirmed set. Everything above is
deployed and none of it reaches a contractor until that one value is in Vercel
and the project is redeployed.

Webhook execution still does not exist. The Hub database still has no backups.
