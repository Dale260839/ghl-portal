# Project Hub — the lock that unlocked itself every time a server woke up

**7 October 2026**
**Live at:** https://project-hub-one-vert.vercel.app

---

## The finding

Sign-in has always been rate limited: five project-code attempts an hour, ten
password attempts in fifteen minutes. That is the thing standing between a
homeowner's project code and somebody guessing it.

It was counted **in the memory of one server**.

The Hub runs on Vercel, which starts and stops servers constantly and runs
several at once. So the count was never really five. It was five *per server
process* — and a new process begins at zero. Someone guessing codes did not
have to defeat the limit; they only had to keep going until a cold start handed
them a fresh allowance, which happens on its own, repeatedly, for free.

The limiter looked right in the code and in every test, because a test runs in
one process.

## What changed

The count lives in the Hub database now, claimed atomically, so every server
draws on the same budget. Specifically:

- **Database time sets the window.** A browser cannot refresh its own allowance
  by lying about the clock.
- **Only keyed hashes of the email and IP are stored** — never a raw address.
- **Successful sign-ins count too**, so a correct guess does not refund the
  budget it spent getting there.
- **It fails closed.** A missing migration, a database error or a timeout
  refuses new sign-ins with a retry message. There is no in-memory fallback,
  because a fallback is the original bug wearing a hat.

GHL sign-in and already-authenticated sessions are untouched.

## The order it was released in, which mattered

Because the limiter fails closed, **the migration had to be live before the
code**. The other way round would have refused every crew and homeowner sign-in
across the whole product until it caught up.

Migration `0022` was installed and verified on the production Hub on 7 October,
**before** the application release. That is the right order and it was followed.

## It was proven against the real database, not a local one

Worth recording, because the tempting shortcut here produces a confident wrong
answer. Local tests queue their queries through a single connection, so they
cannot demonstrate that two servers contending for the same counter behave —
which is the entire claim.

So two genuine PostgreSQL connections were made to contend on one synthetic key:

> Connection A took three claims and held its transaction open for twelve
> seconds. Connection B then took two more, and its third was refused.
> **Five accepted, not six.**

Threshold checks ran inside a rolled-back transaction as the service role. No
real account, address or client record was involved, and nothing a customer owns
was changed. Catalog checks confirmed the counter table has RLS on and that the
browser roles can neither read, write, reset nor execute any of it.

## Also today

**Login recovery and invited-user role boundaries.** A failed password lookup
used to throw an unhandled page error — a database hiccup presented to a
homeowner as a crash. It is a recoverable sign-in refusal now, with a retry.
Alongside it, the role boundaries for invited users were tightened so a stale
invitation cannot resolve to more access than it was issued with.

---

## What is *not* done, honestly

**People behind one IP share one budget.** A crew of four on the same site
Wi-Fi draw on the same allowance, and so do an office full of staff. The limits
are deliberately strict for the pilot. This needs watching with real people
before any decision to loosen the IP path — and the per-account limit should not
be loosened at all.

Deliberate lockout testing must use synthetic accounts. Do not prove the
threshold by locking out Chris, Dale or a client.

And as of this evening, contractor sign-in is still waiting on one environment
variable. None of today's work reaches a contractor until that is set.
