1. Purpose of This Document
This document turns the approved architecture and technical review into an actionable kickoff plan. It states what must be prepared before any heavy building begins, the exact validation tests that gate the project, and the phased development sequence from data foundation to a distributable deployment package.
Read this before starting: the plan is deliberately front-loaded with two cheap tests. If either fails, the approach changes before time is spent building nine objects and dozens of screens. Nothing in Phase 1 onward starts until Phase 0 passes.
2. What We Are Building
BuildSuite stays focused on estimating, proposals, takeoffs, and profitability. Once a proposal is signed, the project is handed off to GoHighLevel (GHL), which runs everything operational — tracking, workflows, communication, approvals, documents, and payments. The three user experiences are not three separate systems. They are three permission-controlled views of one shared GHL project record.

The portals never talk to BuildSuite directly. The handoff is the bridge; GHL owns all operational records created after it.

3. Guiding Principles (Non-Negotiable)
These rules are enforced at the data layer, not just the UI, and hold across every phase.
* One record, three views. The Project Custom Object is the single backbone; visibility is controlled per item, not per system.
* The publishing approval path. Field submits → contractor reviews and edits the client summary → contractor publishes. Field updates are never auto-published to the client.
* The client-facing rule. A record reaches the client only when Client Visible = Yes AND Manager Approval = Approved. Anything else stays internal.
* Authenticated access for anything that matters. Email + project ID is a lookup convenience only. It must never gate approvals, money, or documents — those require GHL portal login.
* Internal data never crosses the boundary. Internal notes, vendor cost, internal labor cost, markup, margin, profit, private messages, and risk assessments are never passed into any client response.
* One shared key. The BuildSuite Project ID is the master identifier across BuildSuite, GHL, and Supabase. Names and addresses change; the ID does not.
* Build shippable slices. Prove the data chain end-to-end before widening scope. Do not build the full accounting, warranty, vendor, and reporting sections until the core connection works.

5. Phase 0 — Validation Sprint (Go / No-Go)
Run both tests before creating all the objects and screens. These are the two things nobody has proven yet, and together they decide whether the whole distribution and live-data model works. Owner: Chris + Pat.
Test A — Snapshot transfer
Effort: ~10 minutes.   Why it matters: the entire per-contractor rollout rides on snapshots carrying custom objects. If they don't transfer, we need a per-account setup script instead — and we want to know that on day one.
Create a Custom Object “BuildSuite Test Project” with fields: Project Name, BuildSuite Project ID, Progress Percentage, Project Stage, Client Visible; plus one association to Contact. Then:
1. Add it to the master build sub-account and create/update the snapshot.
2. Push the snapshot into the test contractor sub-account.
3. Confirm the object, fields, and associations all arrive intact.
4. Confirm workflows can reference the transferred object.
Test B — AI Studio live data
Effort: ~1 hour.   Why it matters: proves AI Studio can display live per-client data — the only piece of the plan nobody has tested. It's the difference between a visual demo and a real portal.
Create one real record and wire a single field into the prototype:


	

Project Name: Johnson Kitchen Remodel     BuildSuite Project ID: BSP-TEST-001
Progress Percentage: 62     Project Stage: In Progress     Client Visible: Yes
Then update Progress 62 → 70 and confirm the AI Studio dashboard reflects the change live.
	



	Gate
If both tests pass → proceed to Phase 1 and build the full Project object, first two workflows, and initial dashboard screens.
If Test A fails → replace snapshot distribution with a per-account setup script / deployment checklist.
If Test B fails → rethink the live-data wiring approach before building any client-facing screens.

6. Development Phases
Each phase produces something demonstrable. Phases 1–4 together deliver the demoable core; Phases 5–6 complete Version 1 and package it for distribution.
Phase 1 — Shared data foundation
Goal: the one record everything reads from exists and is correct. Owner: Chris + Pat.
* Create the Project Custom Object with the demoable-core field set (Section 9) — identity, status, dates, financials, and client-visibility flags.
* Create the BuildSuite™ Project Lifecycle pipeline (20 stages, New Project → Warranty, plus On Hold / Canceled).
* Establish associations: Contact → Project, and Project → Opportunity / Company / team roles. Design for one contact having multiple projects — never assume one contact equals one project.
* Add supporting objects (Milestone, Task, Daily Update, Selection, Change Order, Issue, Message, Punch List, Warranty) as needed — but only what the current phase uses.
Phase 2 — Workflows & the BuildSuite handoff
Goal: a signed proposal automatically becomes a live GHL project that stays in sync. Owners: Dale (workflows), Sing (handoff).
* Extend Send to CRM to stamp project identity onto the contact in the same call: project name, address, contract amount, and the shared BuildSuite Project ID (~1 day, Sing).
* Workflow 1 — New Project Setup: on estimate approved / project created, create the Project record, associate contact and opportunity, assign PM, seed default milestones/tasks, set progress to 10%, prepare portal access.
* Workflow 2 — Project Stage Sync: on opportunity stage change, update the Project's stage, progress, current/next milestone, and notify appropriately.
* Stage sync back into BuildSuite: a scheduled job reads each project's pipeline stage by shared ID and updates the contractor's My Projects view (the “update every hour” idea).
Phase 3 — Contractor Dashboard (real data)
Goal: the control center shows and drives live projects. Owners: Chris + AI Studio.
* Build the initial screens only: Portfolio Overview, Projects List, Project Overview, Project Timeline, Daily Update Review, Client Visibility Settings.
* Wire Overview and Projects to real Project records first, then layer the rest.
* Defer the full accounting, warranty, vendor, and reporting sections until the core connection is solid.
Phase 4 — Client Portal (connected)
Goal: clients see live, approved progress through a secure login. Owners: Chris + Pat.
* Enable GHL's native Client Portal; route contracts, estimates, invoices, receipts, and payments through it (Pay Now → native GHL invoices).
* Connect the AI Studio prototype as the richer project-tracking experience, filtered to the signed-in contact.
* Add the missing pieces the prototype needs: real authentication, live project data, project switcher (multi-project clients), and wired approve / message buttons.
* Enforce Client Visible = Yes AND Manager Approval = Approved on every view; strip internal fields at the data layer.
Phase 5 — Field Interface & remaining Version 1
Goal: the field can submit, and the review-then-publish loop is complete. Owner: All.
* Build the minimal field app: assigned projects, today's tasks, start/complete task, daily update form, photo upload, report issue, submit to PM.
* Keep the flow strict: Field submits → PM reviews → PM edits client summary → PM publishes → client receives.
* Complete remaining Version 1 items: schedule, tasks, documents, client messages, issues, and a basic financial summary.
* Defer to later versions: time tracking, materials inventory, delivery management, offline mode, subcontractor access, detailed budgets, and change-order/selection automation.
Phase 6 — Deployment package & distribution
Goal: build once, deploy to every contractor sub-account. This is the multiplier.
* Once proven in the build sub-account and validated in Alliance Pro Services, package everything into a reusable snapshot: custom objects, fields, pipeline, workflows, forms, calendars, document/contract templates, email & SMS templates, AI Studio experiences, portal settings, roles, and sample data.
* Distribute per contractor sub-account — optionally gated as a paid add-on per the packaging decision.

10. Shared Project ID Standard
The BuildSuite Project ID is the single key that ties records together across systems. It must exist in every layer so records are never matched only by client name, address, email, or opportunity title — those change; the ID does not.
* BuildSuite  •  GHL Project Custom Object  •  GHL Contact / Opportunity  •  Supabase (when used)  •  external API calls  •  workflow webhook payloads.
Format example: BSP-2026-000184
11. Security Guardrails
Authenticated login gates everything that matters
Email + project number/ID can help locate a record, but GHL portal login must control access to: change-order approvals, selection approvals, payments, contracts, documents, private messages, and warranty records.
Internal fields never enter the client response
Enforce at the data layer, not just visually. Never pass to the client: Internal Notes, Vendor Cost, Internal Labor Cost, Markup, Margin, Profit, Private Team Messages, Internal Risk Assessment.
