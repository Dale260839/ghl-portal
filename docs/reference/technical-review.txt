BuildSuite Three-Experience Architecture
Technical Review and Build Plan
Prepared by Sing  |  July 17, 2026
1. Summary
This is the right architecture and I recommend we build it. Keeping BuildSuite focused on scopes, proposals, takeoffs, and profit, then handing the signed project to a GHL-native tracking system, is cleaner than building tracking into BuildSuite. The data foundation comes first, the contractor dashboard before the client portal, and the field-to-manager-to-client approval path protects contractors from publishing anything unpolished. The portal prototype already matches the plan almost exactly. What stands between the prototype and a live product is the data layer, and there are two cheap tests we should run before any heavy building.
2. What the Architecture Gets Right
* One shared project record, three controlled views. The Custom Object foundation with per-item client visibility toggles is the correct backbone.
* The publishing approval path. Field submits, contractor reviews and edits the client summary, then publishes. Internal notes never reach the client. This one rule prevents most of the ways tracking systems embarrass contractors.
* Build order. Contractor dashboard first, client portal last, because the dashboard creates and controls everything the other two display.
* Phased versions. Launching with overview, stages, updates, photos, and documents, then adding selections and change orders, keeps version one shippable.
* Snapshot distribution. Build once, deploy to every contractor sub-account, optionally as a paid add-on. This is the multiplier.
3. How BuildSuite Connects
The portal never needs to talk to BuildSuite directly. GHL sits in the middle and BuildSuite’s side of the bridge is mostly already built:
* Send to CRM is the handoff trigger and it already works. The proposal lands in the contractor’s sub-account, creates the client contact, and goes out for signature. Workflow 1 (New Project Setup) hangs directly off this.
* I will extend the handoff to stamp the project identity. Project name, address, contract amount, and a shared BuildSuite project ID written onto the contact in the same call. The workflow reads those fields and creates the Project record. About a day of work on my side.
* Stage sync back into BuildSuite. A scheduled job reads each project’s pipeline stage by the shared ID and updates the contractor’s My Projects view, the "update every hour" idea. Straightforward once the pipeline exists.
* Everything else is created inside GHL after handoff. Milestones, tasks, daily updates, change orders, and invoices come from the contractor, the field team, and the workflows, not from BuildSuite. That separation is what keeps both systems clean.
4. Client Portal Prototype, Review Findings
I tested the AI Studio prototype page by page, including on mobile. It is genuinely good: the action-required queue, change order cards with cost and schedule impact, the budget view showing only client-safe numbers, daily updates with acknowledge and comment, and the navigation collapses properly on a phone. To go from demo to product it needs:
* The data foundation. Every screen is sample data today; the custom objects have to exist before anything can go live.
* Real login through GHL’s native client portal, filtered to the signed-in contact, with Pay Now routed through native GHL invoices.
* A project switcher, since one client can eventually have multiple projects.
* The approve and message buttons wired to the workflows (change order approval, selection approval, messaging).

6. Security Guardrails
* Anything beyond read-only summary info requires the authenticated portal login. Email plus project ID alone is fine as a lookup convenience but must not gate approvals, money, or documents.
* Internal notes, vendor costs, markups, and margins never render in the client experience, and the prototype already respects this. Keep it enforced at the data layer with the Client Visible flags, not just in the UI.
* The new system should live in a clean dedicated sub-account with its own integration token, then deploy into Alliance Pro Services as the first live test. Clean snapshot source, no tangling with live data.
